# ADR-0012: Public Result Announcement — minimal plaintext store + capability-token (STRAI ID) access

**Status:** Accepted — confirmed by founder (Addendum 2, `docs/reports/SHARLO-M0-009.md`). This is a deliberate, narrow exception to `ADR-0001`/`ADR-0004`'s zero-server-plaintext property, not a departure from it — the exception's narrowness is itself the safety mechanism, and any future proposal to widen it needs the same level of scrutiny this one got, not an assumption that the door is already open.

## Context

Addendum 2 (`docs/SRS.md` `FR-PUBLISH-*`) asks for a public, unauthenticated way for a student to check their own result using a code their teacher gives them (a "STRAI ID") plus their roll number. Every other feature in this product is built around a hard invariant: our backend never receives plaintext student data, because the reader is always an authenticated teacher holding a decryption key the server never sees. A public checker has no key and no account — there is no cryptographic scheme that lets an anonymous stranger decrypt a teacher-encrypted blob. Either this feature doesn't get built, or the teacher explicitly, knowingly hands a minimal subset of plaintext to the server for exactly this purpose.

## Decision

- The teacher clicks "Announce Result" on one already-scored exam — an explicit, opt-in, **per-exam** action, not a setting that changes default behavior for anything else.
- The client extracts exactly four fields from the already-decrypted exam record — student name, roll number, marks, grade — and sends **only those** to a new, minimal Postgres table, `public_results` (`ARCHITECTURE.md` §6). No phone numbers, no other roster fields, nothing from any other exam.
- A new STRAI ID (≥128 bits of CSPRNG entropy, Crockford Base32-encoded in readable groups — `NFR-SEC-13`) is generated fresh for that announcement and stored alongside the row.
- A public, unauthenticated endpoint accepts `(straiId, rollNumber)` and returns that one row's public fields, or a generic "not found" for every failure case (wrong ID, wrong roll number, expired ID) — never a response that distinguishes which.
- The row auto-expires (`app_config.public_result_ttl_days`, default 30, admin-configurable) and is deleted on the owning teacher's account deletion.
- Access control is a **capability token**, not tenant-scoped Postgres RLS: possession of a valid STRAI ID is what authorizes a read, the same pattern as an unguessable share-link. There's no "current user" to scope an RLS policy by, because the requester is anonymous by design.

Full design and the fail-closed/rate-limiting details: `ARCHITECTURE.md` §7a.

## Alternatives considered

- **Don't build it.** A real option, and the founder's Addendum 2 explicitly chose to build it instead — noted here because it's the only alternative that preserves the zero-server-plaintext property with zero exception. Rejected by the founder as a product decision, not an engineering one; this ADR exists to make sure the exception that follows from that choice is as narrow and well-guarded as possible.
- **Aggregates-only** (class average, distribution — never a specific student's raw marks) published instead of per-student results. Smaller exposure surface, but doesn't satisfy the actual requirement (a student checking _their own_ result), so it wasn't the right narrower alternative — noted for the record since it's the same shape of alternative ADR-0010 considered for the School dashboard and rejected there for a similar reason (the feature needs per-individual data, not just aggregates).
- **A per-student secret instead of a shared per-exam STRAI ID** (e.g., a unique code texted/emailed to each student). Rejected: Sharlo has no phone number or verified-email channel for students (deliberately — `FR-PUBLISH-01` explicitly excludes phone numbers from what's ever published), and printing one shared code on a result-card template that every student in the class receives, each looking up only their own roll number, matches how physical result announcements already work (a posted sheet, a shared code) — simpler for the teacher, and the roll-number check still means one student can't read another's row even with the same STRAI ID.
- **Store the published data encrypted too, decrypted client-side using a key embedded in the URL/QR code** (like many "secure share link" products do — a Fernet-style key-in-fragment scheme). Considered seriously: this would let us claim "still zero server-plaintext" even for this feature. Rejected for two reasons: (1) it doesn't actually change the security properties that matter here — anyone with the link/QR can decrypt regardless, so it's the same effective exposure as plaintext-behind-a-capability-token, just with more implementation complexity and a new class of bugs (key-in-URL leaking via referrers/logs, which a plaintext-behind-rate-limiting design doesn't introduce any differently); (2) it would let the "zero server-plaintext" marketing claim technically survive while being misleading in spirit — this ADR would rather have one honestly-labeled exception than a technically-true claim that doesn't match what it implies. See the marketing-honesty note in `docs/reports/SHARLO-M0-009.md`.

## Consequences

- The "we never see your data" claim (used in marketing, `ADR-0001`) needs one honest caveat from here on: _"...unless you explicitly choose to publish specific results for student self-checking."_ This must be stated plainly wherever the broader claim is made publicly, not buried — an accurate caveated claim is a strength (it shows the exception is deliberate and narrow, not a gap someone found later); an uncaveated claim that turns out to have an exception is a trust problem waiting to surface.
- `public_results` is the one table in the schema that needs its own bespoke reasoning every time someone touches it, instead of inheriting the standard RLS pattern everyone else gets for free (`ARCHITECTURE.md` §8) — a real, accepted maintenance cost for this feature specifically, not spread across the rest of the schema.
- Account deletion (`NFR-PRIV-03`) has to explicitly cascade into a non-tenant-scoped table for the first time — a special case in that flow's implementation and its test coverage (`FR-PUBLISH-09`), not something the standard per-`user_id` deletion query handles automatically.
- This is new, genuinely public-facing attack surface (rate limiting, CAPTCHA, enumeration resistance) that nothing else in the product has — the admin panel and API are all authenticated; this is the one anonymous-by-design entry point, and it should get proportionate security review attention for exactly that reason (`docs/TASKS.md` M12, M7's security-review pass).
