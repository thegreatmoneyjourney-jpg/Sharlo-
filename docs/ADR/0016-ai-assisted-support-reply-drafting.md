# ADR-0016: AI-assisted support reply drafting — human-confirmed only, PII-sanitized

**Status:** Accepted — founder directive (Addendum 3).

## Context

`ADR-0014` establishes a general product boundary: no AI/LLM assistance anywhere that touches **student data or exam content**, because a confidently-but-incorrectly-resolved case in that category produces a wrong result with no obvious sign anything went wrong — the same failure mode `NFR-ACC-03` exists to prevent in the scanning engine. That ADR explicitly anticipates this exact situation: "If a future, genuinely different use case seems to want AI/LLM assistance... that's explicitly a new decision requiring the same level of founder sign-off this one got."

Addendum 3 requests one: an AI-drafted first-pass reply for founder support tickets, so a solo founder can respond to support volume faster without typing every reply from scratch. This is a genuinely different case from the one `ADR-0014` rejected:

- It never touches student data or exam content — its input is a support ticket (the _teacher's_ own account/billing/product question) and a founder-maintained knowledge base of generic product information.
- Its output is never applied automatically. A human (the founder) reads every draft and explicitly sends, edits-then-sends, or discards it — there is no code path where an AI-drafted reply reaches a customer without that step. This is the same "AI suggests, a human confirms" shape already used elsewhere in this product (the bubble Review Queue, `FR-DETECT-03`; import column-mapping pre-fill, `FR-IMPORT-02`) — not a new philosophy, an application of the existing one to a new surface.

So this ADR is not an exception carved into `ADR-0014` — it's the new, separately-approved decision that ADR already said such a case would need, and it stays inside that ADR's own underlying principle (deterministic-and-flagged / human-confirmed beats probabilistic-and-silent) rather than relaxing it.

A second, real risk remains and is this ADR's other half: a teacher writing a support ticket will often reference a specific student while describing their problem ("my student's marks in Class 8B are wrong") — not as a rare accident, but as an ordinary, expected way of describing a scanning/grading issue. If ticket content is forwarded to a third-party AI provider's API to generate a draft, that's a real boundary crossing the zero-knowledge architecture doesn't otherwise have to think about (support tickets, unlike exam data, necessarily have to be human-readable by support staff to be useful — the concern here is specifically about what leaves our infrastructure to a third party, not about the ticket existing in our own database).

## Decision

1. **Draft-only, never auto-sent.** The AI provider's output is written to the ticket as a **draft** (`support_messages.sender_type = 'ai_draft'`, `sent_at` left null). No code path sends it, edits it into the sent-message record, or notifies the customer until the founder takes an explicit send action in the admin panel. This is enforced the same way the bubble-detection guarantee is: it's the one condition under which the reachable-outcome set for an AI-drafted message includes "delivered to a customer," so it's the one thing worth stating as a hard invariant, not just a UX default.
2. **Generic knowledge base only.** The knowledge base the AI reads (`support_kb_articles`, `ARCHITECTURE.md` §6) contains only product/company information the founder writes and maintains — docs, FAQs, pricing, common troubleshooting. It never contains, references, or is populated from any individual user's or student's data. This is a content-policy invariant for what goes _into_ `support_kb_articles`, not something code can fully enforce — call it out in the admin UI that authors this content.
3. **PII sanitization pass before any request leaves for the AI provider.** Before a ticket's content is included in the prompt/context sent to the AI provider, it passes through a masking function that redacts patterns that look like roll numbers, long digit sequences (a fixed-length-digit-run heuristic, generous enough to catch roll numbers, phone-number-shaped strings, and ID-shaped strings), and other likely personal identifiers. This runs on **every** outbound call, not just ones a human decides "might" contain something sensitive — the point of a routine, expected input category is that judgment calls are exactly what a systematic pass is for.
4. **Provider-agnostic integration.** The AI provider is a pluggable adapter (an `AiProviderAdapter` interface: prompt in, draft text out) configured via the credential store (`ADR-0017`) — not hardcoded to one vendor, matching this codebase's existing `PaymentProviderAdapter` pattern (`ARCHITECTURE.md` §10) for the same reason: swapping providers later shouldn't be a redesign.

## Alternatives considered

- **No AI assistance for support at all, founder types every reply.** The status quo, and still the fallback if this doesn't work well in practice. Rejected as the default going forward on the founder's own request — support-reply drafting is exactly the kind of bounded, always-reviewed, non-student-data task this pattern is good at, unlike the import-matching case `ADR-0014` rejected.
- **Sanitize only when a ticket "looks like" it might contain personal data.** Rejected — as noted above, referencing a specific student while describing a support issue is ordinary, not an edge case, so a judgment-call trigger would miss the routine case, not just the rare one. Sanitizing unconditionally is cheap and removes the judgment call entirely.
- **Auto-send high-confidence drafts.** Not requested and explicitly rejected by the shape of the founder's own instruction ("never sent automatically... reviews and sends... every reply manually"). Also would reintroduce exactly the silent-wrong-output risk this ADR's framing exists to avoid, just in a support-ops context instead of a data-processing one.

## Consequences

- `support_tickets`/`support_messages`/`support_kb_articles` (`ARCHITECTURE.md` §6) are ordinary plaintext-in-Postgres tables — not held to the client-side-encryption standard `NFR-SEC-02` sets for student data, because they aren't student data; they're the founder's own support-operations records, which have to be plaintext-readable by the founder to be useful at all. The privacy-sensitive boundary this ADR actually protects is the outbound call to the AI provider, not storage — worth stating plainly so a future reader doesn't assume support tickets need the same encryption treatment as `examResults` and either over-build or, worse, misjudge where the real control is.
- The sanitization function needs its own test suite (a fixture set of ticket bodies containing roll-number-shaped and digit-sequence-shaped strings, asserting they're masked before the outbound payload is constructed) — the same "this is the enforcement mechanism, not just documentation of intent" standard `bubble-fill.test.ts`'s never-guesses suite already sets for `NFR-ACC-03`.
- A wrong or unhelpful AI-drafted reply costs the founder a few seconds to discard or rewrite — bounded, low-severity by design, because nothing downstream of the draft is authoritative until a human acts on it.
