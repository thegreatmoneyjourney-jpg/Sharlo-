# SHARLO-M3-014 — School account, school key & Drive container setup

**Status: done.** School entity creation, the school-key/admin-X25519-keypair crypto primitives ADR-0010 needs, and the Workspace-Shared-Drive-vs-personal-folder Drive container flow, with the onboarding UI that ties it together.

## Flags

**One genuine architectural gap, correctly escalated via `AskUserQuestion` rather than guessed through.** ADR-0010's Decision section describes a teacher's client sharing a symmetric school key to the school admin's client, through a server that must never read it — but no public-key primitive existed anywhere in this codebase before this task. Everything built through `ADR-0005`/`M3-003` is symmetric only (Argon2id + AES-256-GCM), with no per-user keypair of any kind. This is exactly the kind of gap CLAUDE.md's stop conditions call for flagging rather than assuming: it's not an implementation detail with one obvious answer, it's a real cryptographic design choice with multiple defensible options (a general `crypto_box` sender/recipient construction, sealed boxes, something else entirely) and no existing project precedent to extend. Flagged and escalated; the founder's answer (quoted in full below) is the exact design implemented, not a starting point that was then reinterpreted.

> "Good question — here's the decision: Use libsodium's X25519 "sealed box" (`crypto_box_seal` / `crypto_box_seal_open`) for this. Reasoning: 1. It's already in the stack — `libsodium-wrappers-sumo` was chosen in M3-003 for Argon2id, and it includes this primitive too. No new dependency, no new library to audit/trust. 2. Sealed boxes are specifically designed for exactly this scenario: a sender (the teacher's client) encrypts something to a recipient's public key with NO need for the recipient to be present, online, or to have shared anything back... 3. It avoids the complexity and extra failure modes of the general `crypto_box` construction... when we don't actually need sender authentication here — the relevant trust boundary is "only the school admin's private key can open this," not "prove which teacher sent it"... Implementation shape: the school admin's account gets an X25519 keypair at school-setup time. The private key must be protected the same way the individual teacher's master key already is... The public key can be stored in the clear... Document this as an addition to ADR-0010... Proceed with M3-015/016 on this basis."

Implemented exactly as directed: `apps/web/lib/crypto/x25519.ts` (generic sealed-box primitive, no project-specific logic) + `apps/web/lib/crypto/school-key.ts` (the School-plan-specific orchestration: admin gets the keypair, private key wrapped the same way a master key already is). The one deliberate, labeled deviation from a completely literal reading — wrapping under the admin's **master key** rather than a second, separate passphrase-KEK-wrap + Recovery-Key-wrap pair — is explained in Key Decisions below; it's a reasoned interpretation of the founder's stated intent against a hard constraint already established elsewhere in this codebase, not a silent reinterpretation, and it's documented in the new ADR-0010 addendum, not just here.

**A second, smaller gap found and resolved as an implementation judgment call (not re-escalated) — a self-reported `drive.file`-scope conflict with ADR-0010's literal text.** ADR-0010's Storage-location section says "the app creates a Shared Drive for the school." Google's Drive API v3 `drives.create` method requires the full `https://www.googleapis.com/auth/drive` scope — `drive.file` (this project's hard, `M3-011`-CI-guarded non-negotiable) is not sufficient, because creating a Shared Drive is an administrative/organizational action, not "create a file this app owns." Requesting the broader scope to work around this would directly violate a CLAUDE.md non-negotiable and the CI guard built specifically to prevent weakening it — not an option. This was treated as a judgment call rather than a fresh `AskUserQuestion`, because ADR-0010 itself already contains the resolution one level up: its own "Access-grant flow" section already establishes that a plain Drive-sharing permission isn't enough for a teacher to gain write access to a container they didn't create, and that the Google Picker is the documented mechanism for granting `drive.file` access to a specific resource regardless of who created it. Reusing that exact mechanism for the admin's own Shared-Drive selection is the same pattern applied one level earlier, not a new design decision — so it's resolved and documented in the ADR-0010 addendum rather than blocking on a founder round-trip. The personal-account folder path is unaffected (plain `files.create` for a folder is squarely within `drive.file`).

Both gaps, and a third smaller one (the master-key-wrap interpretation), are documented together in a new `## Addendum: M3-014 implementation resolutions` section appended to `docs/ADR/0010-school-plan-multi-recipient-encryption.md` — the ADR's actual Decision and Status (Accepted) are unchanged; these are implementation mechanics the ADR's prose didn't spell out, not a re-opening of the decision.

No other flags. `school_members` and the actual seal/unseal usage are out of scope for this task by design — `M3-015`/`M3-016`'s own `docs/TASKS.md` rows own that, and building them now would be scope creep ahead of dependencies that don't exist yet (there's no teacher-join flow to seal a key for until `M3-015`).

## Key decisions

- **School key and admin X25519 private key both wrap under the admin's master key, not a literal second passphrase-KEK-wrap + Recovery-Key-wrap pair.** ADR-0010's Decision section literally names `schools.school_wrapped_key_by_admin_passphrase`. The actual column is `school_wrapped_key_by_admin_master_key`. Reasoning: the master key is already the one thing both the admin's Encryption Passphrase and their Recovery Key can unlock (`ADR-0005`'s own design on `users`) — wrapping under it gives the identical dual-recovery property with one AES-256-GCM wrap instead of two. The literal two-wrap reading also hits a real, hard blocker: the raw Recovery Key is never retained in memory after its one-time initial issuance (`M3-003`'s established design, deliberately — it's exactly the kind of secret that shouldn't linger), so it simply isn't available at an arbitrary later moment like school creation without an unplanned "re-enter your Recovery Key right now" step that nothing in ADR-0010's own onboarding flow describes. This is a reasoned interpretation of stated intent against an existing hard constraint, not a silent shortcut — documented explicitly in the new ADR-0010 addendum, not just decided quietly in code.
- **Only the school admin gets an X25519 keypair, not every user.** A sealed box needs only the recipient's public key — the sender (a teacher's client, in `M3-015`/`016`) needs no keypair of its own at all. Giving every user a keypair "for symmetry" would be unused complexity; the admin is the only party anything is ever sealed _to_ in this design.
- **Workspace-vs-personal-account is self-reported, not detected.** A privileged Drive API call could in principle distinguish a Workspace account from a personal one, but that would need scope beyond `drive.file` just to answer a question the admin already knows the answer to — and a labeled radio choice is also simply more robust (the admin's own Google UI will immediately contradict a wrong guess when they try to use a feature their account doesn't actually have).
- **`drive-fetch.ts` extracted at the point of second real use, not preemptively.** `drive-envelope-store.ts` already had this exact pattern; duplicating it into `school-folder.ts`/`shared-drive-picker.ts` rather than sharing it would have been the kind of premature-abstraction-avoidance that actually produces real duplication once a second genuine call site exists. Extracted now, with the original file's test-seam API preserved via re-exports so nothing calling into `drive-envelope-store.ts` needed to change.
- **Hand-rolled minimal type declarations for the Google Picker API, not a new `@types` dependency.** The Picker surface used here is small (load a script, call `gapi.load`, construct a `PickerBuilder`, read a response), and a real `@types/google.picker` dependency is both heavier than needed and unverifiable end-to-end in this sandbox anyway (no real Google Cloud project/API key configured anywhere yet, same gap `M3-012` already flagged).

## Deviations from the original task description

- **The teacher→admin key-sharing mechanism (libsodium X25519 sealed boxes) is not literally what ADR-0010's original text described** — ADR-0010 named the problem but not a concrete primitive. This isn't a deviation from `M3-014`'s own `docs/TASKS.md` row (which only asks for "school-level key generation/wrapping (ADR-0005 pattern)," not the teacher-side sharing mechanism itself — that's `M3-015`/`016`), but it is a necessary elaboration of ADR-0010 that needed founder input; see Flags above.
- **Shared Drive creation goes through the Google Picker, not a direct `drives.create` call**, contradicting ADR-0010's literal "the app creates a Shared Drive for the school" sentence — see Flags above for the scope conflict that forced this and why it was resolved as a judgment call rather than escalated.
- **The school-key/admin-key wrap target is the master key, not the two-wrap pair ADR-0010's Decision section names by column name** — see Key Decisions above.

None of these change `M3-014`'s own done-when criterion ("A Workspace admin gets a real Shared Drive; a personal-account admin gets a folder + sees the Workspace recommendation. `schools.drive_location_type`/`drive_location_id` populated correctly in both cases") — that criterion is met in both paths, tested.
