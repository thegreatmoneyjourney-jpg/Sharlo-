# SHARLO-M3-004 — Recovery Key onboarding UX + reminder cadence

**Status: done.** Split per the founder's Addendum 6/7 instructions: the onboarding-UX half of this task's original description (forced confirmation, download, unmissable messaging) shipped as part of `M3-003`, since `M3-003`'s own signup flow needed it to actually be real. This task delivers the remaining half — the 7-day/30-day reminder cadence — fully built and tested for its scheduling/banner logic, with the Resend email integration wired in behind a swappable interface but not yet exercised end-to-end, exactly as the founder's Addendum 7 instructed given `M0-008` (domain/Resend account) isn't provisioned yet.

## Flags

1. **A real data-leak bug was caught here by a test, not by review — the most important thing in this report.** While building the Recovery Key reconfirmation flow, the confirm handler was initially written to forward the _entire_ rotation-result object to the function that POSTs to the server — which included the raw plaintext `recoveryKeyDisplay`, the actual Recovery Key. This would have sent the key itself to our server over the network, a direct violation of the zero-knowledge architecture this entire subsystem exists to protect. TypeScript's structural typing did not catch it: the "excess property check" that would normally flag an object literal with extra fields only applies when a literal is passed _directly_ to a typed parameter — here, a variable (`step`) was passed through a call site, which TypeScript allows silently. A `toHaveBeenCalledWith` test assertion with the exact expected shape caught it immediately (that matcher fails on extra properties, not just missing ones); a looser "was this called" assertion would have missed it entirely. Fixed by constructing a fresh, narrow object literal at the call site instead of forwarding the wider one, and the test was strengthened with an explicit assertion that the raw key is never present in what gets sent, as a durable regression guard. Given the founder's original mandate for `M3-003` was specifically about not trusting "the wrapping logic looks symmetric," this is exactly the kind of thing that mandate was written to catch — flagging it prominently rather than glossing over it.
2. **The reminder cadence does not restart after a rotation — a deliberate, literal reading of the spec text, not an oversight.** `ADR-0005`'s addendum says an active re-confirmation "stops" the reminders; it doesn't describe a repeating cycle. So `rotateRecoveryKey` sets `recovery_key_reminder_dismissed_at` and nothing else — the account is excluded from all future sweeps permanently, even though the underlying Recovery Key itself changed. If the founder actually wants indefinite recurring reminders (e.g., every ~30 days forever, restarting after each rotation), that's a real product decision beyond what FR-AUTH-09's literal acceptance criterion ("exactly one 7-day and one 30-day reminder... and no more after an explicit re-confirmation action") asks for — flagging it now rather than guessing either way.
3. **A pre-existing timeout-margin issue in `M3-003`'s own test file surfaced during this task's full-suite verification runs** (not something this task's own code caused) — `lib/crypto/master-key.test.ts`'s passphrase-change test chains 3-4 sequential _real_ Argon2id computations in one `it()` block, which occasionally exceeded vitest's 5000ms default under this sandbox's variable CPU availability. Root-caused (not just re-run and hoped) and fixed with a global `testTimeout: 20000` in `vitest.config.mts`, justified by the deliberate choice (per `M3-003`'s own rigor mandate) to run real, unmocked KDF operations in that test file rather than mocking them.
4. **The Resend "from" address is stored alongside the API key in `integration_credentials`** (`provider: 'resend'`, `keyName: 'from_address'`), even though it isn't itself a secret. Judged simpler than introducing a new non-secret app-config table for one string, given the credential store is already the one admin-managed place this kind of provider setting lives. Revisit if a broader config table gets built later for unrelated reasons.
5. **`M0-008` (the actual Resend account, domain, DKIM/SPF/DMARC) remains unprovisioned** — per the founder's own Addendum 7 acknowledgment, this is expected and being worked on externally. `ResendEmailSender` is real, complete, production-ready code; it simply cannot succeed yet because `getCredential` has nothing to return. Every caller handles that failure gracefully (logs, counts it, leaves the reminder unsent for retry the next day) rather than crashing.

## What was built

**API (`apps/api/`):**

- `email/email-sender.ts` — the `EmailSender`/`EmailMessage` interface, matching `docs/ARCHITECTURE.md` §10's `PaymentProviderAdapter` pattern (the rest of the app depends on the interface, never on Resend directly).
- `email/resend-email-sender.ts` — the real Resend HTTP integration, reading its API key and from-address from `integration_credentials` (never a hardcoded env var, per `ADR-0017`).
- `email/recovery-key-reminder-email.ts` — builds the 7-day/30-day email content; never mentions students, rolls, classes, or exams (`ADR-0011`), only a link back to the teacher's own `/settings`.
- `scheduler/recovery-key-reminders.ts` — `runRecoveryKeyReminderSweep` (the actual scheduling rule, against the privileged/owner DB connection) and `startRecoveryKeyReminderScheduler` (the in-process daily runner `ADR-0011` calls for — runs once at startup, then every 24h).
- `auth/account-encryption.ts` — added `getRecoveryKeyReminderStatus` (computes the banner's show/hide condition) and `rotateRecoveryKey` (persists a new Recovery Key wrap + verifier, sets `recovery_key_reminder_dismissed_at`).
- `routes/encryption.ts` — added `GET /account/recovery-key-reminder-status`, `POST /account/recovery-key-reminder-confirm`.
- `index.ts` — wires the scheduler with a real privileged DB connection and a real `ResendEmailSender` at process startup; stops it on `SIGTERM`.

**Web (`apps/web/`):**

- `app/(app)/layout.tsx` — the `(app)` route group's first shared layout (none existed before), deliberately minimal: just the reminder banner above `{children}`.
- `app/(app)/recovery-key-reminder-banner.tsx` — the in-app persistent banner. An "X" hides it for the current page view only (component-local state, never persisted) — a passive dismiss doesn't count per the ADR's own wording, so it returns on the next navigation until the teacher actually reconfirms.
- `app/(app)/settings/recovery-key-reveal-card.tsx` — extracted from `M3-003`'s `SetupFlow` into a shared presentational component (show the key, offer a download, require an active checkbox before continuing), now used by both the initial-setup flow and this task's reconfirm flow.
- `app/(app)/settings/settings-client.tsx` — added `ReconfirmRecoveryKeyFlow`: requires the current passphrase (to unwrap the master key), rotates to a new Recovery Key, shows/downloads/confirms it via the shared card, then persists.
- `lib/api/account-encryption-client.ts` — added `fetchRecoveryKeyReminderStatus`, `submitRecoveryKeyReminderConfirm`.

## Key decisions

- **Exactly one 7-day and one 30-day reminder, stopping for good on active re-confirmation** — see Flag 2.
- **Re-confirmation = rotation, not re-display** — the same reasoning `M3-003`'s report already established (the raw original Recovery Key is never retained anywhere), now actually implemented and tested end to end rather than just planned.
- **The sweep runs on the privileged/owner connection**, the same category of operation as a migration or the seed script — reading every account's reminder state is inherently cross-tenant, not something `withTenantContext`'s RLS-scoped connection is for.
- **A failed send leaves the `*SentAt` column unset** so the next day's sweep retries it, rather than marking a reminder "sent" when it wasn't — this is what makes today's inevitable "no Resend account yet" failures safe rather than silently losing reminders.

## How it was tested

- **Scheduling logic** (`apps/api/test/recovery-key-reminders.test.ts`, real Postgres): no reminder before 7 days elapsed; the 7-day reminder sent and recorded once due; not re-sent on a later sweep once already sent; both the 7-day and 30-day reminders sent in one sweep for a 31+-day-old account that never had either sent; the 30-day reminder alone when the 7-day one already went out; an actively-dismissed account excluded regardless of how long ago it was issued; a failed send leaves the sent-at column unset and counts as a failure rather than crashing the sweep; multiple eligible candidates in one sweep are all processed, not just the first.
- **Resend integration** (`apps/api/test/resend-email-sender.test.ts`, real Postgres for the credential lookup, mocked `fetch`): the correct HTTP request shape (URL, auth header, body); a clear thrown error on a non-OK response; the expected-today failure mode (no credential stored yet) throws with a clear message rather than silently doing nothing.
- **Email content** (`apps/api/test/recovery-key-reminder-email.test.ts`): addressed correctly, links to the right settings URL, distinguishes the 30-day "final reminder" subject from the 7-day one, and — checked with a word-boundary match specifically to avoid a false positive against the test's own "example.com" fixture URL — never mentions students, rolls, classes, or exams.
- **API routes** (`apps/api/test/encryption-routes.test.ts`, real Postgres): both new routes reject an unauthenticated request; the status route reports the correct before/after-7-days state; the confirm route rejects before setup, persists the new recovery wrap and verifier on success, leaves the passphrase wrap untouched, and stops the banner.
- **Web** (real component tests, network/crypto mocked — mirroring `M3-003`'s own established split of "this proves UI wiring, not cryptographic correctness, which the crypto module's own tests already cover exhaustively"): the banner renders nothing while loading, on a fetch failure, or when `showBanner` is false; renders and links to `/settings#recovery-key` when true; the "X" hides it for that view. The reveal card: checkbox gates the continue button; busy/error states; download triggers `URL.createObjectURL`. The reconfirm flow: unwraps with the current passphrase, calls the rotation primitive, requires the confirmation checkbox, and — the regression test for Flag 1 — asserts the exact payload sent to the server, including an explicit check that the raw Recovery Key display string is never present in it.
- **Full-suite verification**: `npm run ci` (format + lint + typecheck + test) green on both workspaces against a real local Postgres instance, not skipped. A real `next build` production build still succeeds and still lists `/settings` as a generated route (the new shared `(app)` layout doesn't add a route of its own). `docker compose config` still validates.
