# HANDOFF-SUMMARY — Developer handoff (Claude Code → Cline), 2026-10-03

## Flags — things genuinely unresolved, needing the founder's input, not guessed at

Two real findings came out of the reconciliation audit (Section 1 of the handoff prompt) that no amount of careful reading of this project's existing docs could resolve on their own — both are now tracked explicitly rather than left as something the next developer has to rediscover.

1. **"Fee Tracker" — one of exactly four pillars the founder has named as locked v1 scope (Addendum 6, reconfirmed Addendum 9) — has no specification anywhere in this codebase.** No `FR-FEE-*` requirement IDs, no data model, no milestone, nothing beyond the two-word gloss "teacher tuition tier + principal/school rollup." Confirmed by an exhaustive grep across `docs/SRS.md`, `docs/ARCHITECTURE.md`, `docs/TASKS.md`, every ADR, and every existing task report — the phrase "Fee Tracker" and the word "tuition" appear in exactly two places in the entire project (`docs/SRS.md` §10's out-of-scope list intro and `docs/TASKS.md`'s `BACKLOG-003` row), both times only as a label in a list of the four pillars, never as an actual spec. The most likely explanation, found while tracing it: Addendum 6 (which first named the four pillars) never received the same "incorporate into SRS/ARCHITECTURE/TASKS" governance pass that Addenda 2, 3, 4, 5, and 9 each explicitly got — only the label survived into the live docs, not the requirements behind the fourth pillar.
   - **Resolution so far:** `docs/SRS.md` §5.17a documents the gap explicitly (what's missing, why it can't be inferred, and what data-classification question needs answering — is this student-PII-adjacent data needing the same client-side encryption as attendance, or something else). `docs/TASKS.md` adds `M13 — Fee Tracker ⚠️ SPEC NOT WRITTEN — DO NOT START` as an explicit placeholder milestone with zero tasks, so it's visibly tracked rather than silently absent. `HANDOFF.md` §3.1 and `.clinerules` §4's table both flag it as a standing stop-and-build-nothing item.
   - **What's needed from the founder:** a real requirements conversation — what a fee record contains, how a payment is recorded (manual entry? receipt numbers? currency/period assumptions?), what "principal/school rollup" means concretely, and whether this is the same billing domain as `FR-BILLING-*`/`M4` (Sharlo's own SaaS revenue) or a completely separate one (a school's own fee collection from its own students' parents — which the "teacher tuition tier" phrasing suggests, and which would have nothing to do with Paddle/Bank Alfalah at all).

2. **The School-plan "fallback folder path" teacher-removal continuity mechanism may not actually work, and until now there was no tracked task to find out.** `M3-018`'s own report and `ADR-0010`'s addendum item 5 already flagged real doubt (Google's Drive ownership-transfer API appears to require the recipient's consent even when an admin initiates it, which would make the admin-alone self-upgrade call this mechanism relies on fail silently) — but that finding sat in a report and an ADR addendum with no task anywhere actually assigned to resolve it before the School plan ships to real customers.
   - **Resolution so far:** `docs/TASKS.md` adds `M7-017` (new), explicitly pre-launch-blocking for the School plan specifically (not the individual Teacher plan), referenced from `M7-015`'s own launch-checklist sign-off task so it can't be silently skipped. It requires testing against a **real** Google Drive account — something this project has never had configured anywhere, sandbox or CI — so part of this task's own first step is provisioning one.
   - **What's needed from the founder (only if the mechanism is confirmed broken):** a decision between disclosing the weaker guarantee honestly in product copy (the lower-effort path) versus building a different mitigation (e.g., requiring the departing teacher's own session to cooperate before access is revoked, which has its own problems in a genuinely adversarial departure). `M7-017`'s own spec is explicit that this choice is the founder's, not whoever runs that task's.

One smaller, already-fixed item worth naming here rather than burying in the "what was built" section below: `docs/SRS.md` §8's key-decision-log item 7 (the `NFR-SEC-12` free-tier-gating resolution) still read "PROPOSED, flagged for founder confirmation, not yet a settled resolved" even though `NFR-SEC-12`'s own entry and `docs/ARCHITECTURE.md` §15 resolution-log item 7 have both said "RESOLVED, founder-confirmed" since `ADR-0015` was written weeks ago — a stale, internally-contradictory doc-sync gap, not a live open question. Fixed in place; flagged here only so it's visible that this was found and corrected, not silently glossed over.

## Key decisions made along the way

- **M4/M5/M7's new task IDs are a clean renumbering, not an additive append.** Nothing has ever been built or reported against any `M4`–`M12` task ID (unlike `M0`–`M3`, where IDs are referenced from real commits/reports and were therefore left untouched, copied verbatim into the new file) — so there was no backward-compatibility reason to preserve old numbering or leave cancelled-task placeholder IDs (the original `M5-006`/`M7-010` "ads" placeholders, kept there specifically so already-shipped later IDs wouldn't shift) now that the whole milestone was being renumbered anyway. The ads cancellation itself is still noted in prose at the top of `M5`/`M7` in `docs/TASKS.md`; it just no longer occupies a numbered slot.
- **Fee Tracker got a placeholder milestone (`M13`), not a Backlog entry.** Backlog is explicitly for things _not_ in v1 scope (`BACKLOG-001`/`002`: approved-but-deferred; `BACKLOG-003`: discussed-and-declined). Fee Tracker _is_ in locked v1 scope per Addendum 6/9 — it just has no specification yet. Filing it as a Backlog item would misrepresent it as optional or deferred, which it isn't; a milestone placeholder that explicitly says "do not start" keeps its actual status (in-scope, unspecified) visible and correct.
- **The new `M7-017` (Shared Drive ownership-transfer verification) was written to require testing against a real Google Drive account as its own first step**, rather than being satisfied by more mocked testing — because the entire point of the finding it addresses is that this specific mechanism has _never_ been checked against anything real, and more of the same kind of testing that already missed the real-world behavior wouldn't resolve the actual doubt.
- **The doc-tightening pass (Section 4) was scoped to `docs/SRS.md`, `docs/ARCHITECTURE.md`, `docs/TASKS.md`, and the ADRs — not the already-shipped task reports in `docs/reports/`.** Those reports are historical record of already-founder-confirmed milestones (M0–M3); re-litigating judgment calls made during work the founder already signed off on would be re-opening settled decisions, not tightening ambiguous forward-looking specs. This matches `CLAUDE.md`'s own stated principle that reports are where history lives and shouldn't be rewritten after the fact.
