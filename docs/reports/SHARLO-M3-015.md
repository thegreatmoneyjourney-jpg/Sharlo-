# SHARLO-M3-015 — Teacher-join access grant flow (Drive share + Picker)

**Status: done.** Admin adds a teacher by email, which shares the school's Drive container with them; the teacher completes the one-time Google Picker step that actually grants `drive.file` access to that container. `FR-SCHOOL-02` end to end, except the dual-encrypted write it protects (`M3-016`, not built here).

## Flags

**A real Postgres RLS limitation was found and fixed while building this — not a design choice, a hard constraint discovered by actually testing against real Postgres.** The natural first design gave `schools` a teacher-facing SELECT policy subquerying `school_members` (so a teacher could read their school's Drive location/public key), while `school_members`'s own admin policy necessarily subqueries back into `schools` (so an admin can manage members of schools they own). Running this against real Postgres immediately failed with `ERROR: infinite recursion detected in policy for relation "schools"` — Postgres's RLS cycle detection operates on the policy reference graph, not on whether the actual predicate values would terminate, so any A→B→A cross-table policy reference between two RLS-protected tables is rejected outright, full stop, regardless of how the predicates are written.

This is reported here as a flag rather than just folded silently into "what was built" because it forced a real design change partway through the task, not a refinement: `schools` now has **no** teacher-facing policy at all, and the plan (stated nowhere in `ADR-0010`'s own text, which predates this discovery) is instead to denormalize whatever a teacher legitimately needs onto their own `school_members` row at insert time. This is documented in `schema.ts`'s own doc comment on `school_members` and in `ARCHITECTURE.md`'s resolution log (item 22) as the pattern any future task (`M3-016`'s own need to read the admin's X25519 public key) should follow — not re-attempt a teacher-facing `schools` policy and hit the same wall.

**A second, smaller precondition was found and resolved as a normal implementation judgment call, not escalated**: `addTeacherToSchool` rejects a matched account whose `authProvider` isn't `'google'` (`wrong_auth_provider`). Neither `FR-SCHOOL-02` nor `ADR-0010` says this explicitly, but it follows directly from `ADR-0004`'s existing architecture (Drive access requires a real Google-authenticated account) — a local-only/email-OTP teacher has no Drive access to share in the first place, so silently creating a membership row for one would just produce a permanently-stuck "pending Drive access" state with no way to ever resolve it. This didn't need a fresh founder decision; it's a direct, mechanical consequence of a decision (`ADR-0018`, local-only mode) already made.

**A third item, found while re-reading `M3-014`'s own ADR-0010 addendum before starting this task, is flagged here rather than silently carried forward or guessed at — it doesn't block `M3-015` itself, but it will block `M3-016` if not resolved first.** `M3-014` built an X25519 keypair for the school **admin only**, reasoned (and founder-directed, Addendum 9) as "a teacher's client seals to the admin's public key" — but sealed boxes are strictly one-directional: with only the admin holding a keypair, the admin can _receive_ sealed data from anyone, but cannot seal anything _for_ a specific teacher to receive (that would need the teacher to hold a keypair instead). This means `schools.school_wrapped_key_by_admin_master_key` — the one persisted, shared symmetric "school key" `ADR-0010`'s original Decision text describes being handed from the admin to each joining teacher — is **never actually distributable to a teacher** under the keypair assignment `M3-014` shipped. The only cryptographically coherent reading of what's already built is that each teacher's exam-finalize write (`M3-016`) seals its own payload (or a fresh one-off key) directly to the admin's existing public key, hybrid-encryption-style, with no shared "school key" ever reaching a teacher's hands at all — which leaves the persisted `schools.school_wrapped_key_by_admin_master_key` column and `generateSchoolKey()` with no clear remaining purpose in the live data flow. Not resolved here, since it's `M3-016`'s concrete finalize-time design that actually needs the answer, not this task's Drive-sharing flow — but recorded now so `M3-016` starts from this finding instead of re-deriving it, and so the founder can weigh in on whether the persisted school key should simply be dropped as dead weight, or is intended for some admin-side purpose not yet described anywhere.

No other flags. `school_members`/the actual seal/unseal usage from `M3-014`'s own addendum is now built (the table) except the sealing itself, which is still correctly `M3-016`'s scope, not this task's.

## Key decisions

- **Denormalize onto `school_members`, never attempt a teacher-facing policy on `schools`.** Covered in Flags above — this is the actual load-bearing decision of the task, found necessary by hitting a real Postgres error, not chosen from a menu of equally-valid options.
- **Catch `already_member` via the real unique-constraint violation, not a pre-check.** The admin's own tenant-scoped connection can't see a membership row under a _different_ admin's school at all (RLS correctly hides it), so there's no way to check "is this teacher already a member of some school" ahead of the insert without bypassing RLS. Relying on the constraint itself is both simpler and more correct — found the hard way when the first version let the raw `DrizzleQueryError` escape as an unhandled 500 (the real Postgres error lives on `.cause`, not `.code`, for drizzle-orm's own wrapped errors), fixed and covered by a dedicated route test.
- **Update the member list before, not after, attempting the Drive share.** The membership row is the real, already-committed state once the add API call succeeds; a subsequent Drive-share failure is a separate, narrower problem that must not make the teacher vanish from the admin's view or get reported as "failed to add." Found via a test that initially asserted the wrong (member disappears, generic error) behavior, corrected before considering the task done.
- **The teacher's Picker is scoped to "not owned by me."** The admin's own Shared-Drive-creation Picker (`M3-014`) defaults to the admin's own files since they're creating/selecting something of their own; the teacher is finding something someone _else_ shared, so the opposite default is correct UX, not just a stylistic choice.
- **No speculative second "prompt" component for the finalize-time check.** `ensureSchoolDriveAccess` is built and tested in isolation, but no modal/inline-error component was built to decorate it, since the real call site (`M3-016`'s finalize write) doesn't exist yet to give that decision real context. The standing banner already satisfies `FR-SCHOOL-02`'s "clear, specific prompt" requirement in the meantime.
