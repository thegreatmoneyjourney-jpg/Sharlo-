# SHARLO-M3-005 — Local-only mode

**Status: done.** This report covers the whole task in two parts, shipped as two PRs: the auth-mechanism prerequisite (`ADR-0018`, email + OTP — PR #48, already merged) and the product feature this task's row originally described (IndexedDB storage, persistent warning banner, Export/Import backup file, and the local-only signup UI that ties the two together). Both halves are done; `docs/TASKS.md`'s `M3-005` row can now be marked done in full.

## Flags

1. **A genuine architectural gap, stopped on rather than guessed through (Part 1).** Starting this task surfaced that `FR-AUTH-06` (local-only mode) had no way for a teacher to authenticate at all — every account mechanism built through `M3-004` is Google-OAuth-specific. Flagged via `AskUserQuestion` rather than assumed; the founder's response is the exact spec `ADR-0018` documents. Full account preserved below under "Part 1."
2. **A documentation/implementation mismatch found while building the storage layer, not previously noticed.** `ARCHITECTURE.md` §7's illustrative envelope JSON shows the encrypted payload split into three separate base64 fields (`iv`, `ciphertext`, `authTag`). The actual, already-tested crypto primitives (`apps/web/lib/crypto/aes-gcm.ts`'s `aesGcmEncrypt`/`aesGcmDecrypt`, built in `M3-003`) produce and expect a single combined blob (`iv || ciphertext+authTag` — WebCrypto appends the auth tag to the ciphertext automatically). Nothing has written a real envelope yet to force resolving this either way, so it wasn't silently picked one way — `local-envelope-store.ts` is deliberately typed generically enough (`recordId`/`type`/`schemaVersion` required, everything else an open payload) that it doesn't need to take a side. Whichever task first writes a real encrypted envelope (`M3-006` onward) should reconcile this against the real primitive, not the doc's illustration — flagged here and in that module's own doc comment so it isn't rediscovered from scratch.
3. **`M3-005`'s original acceptance criterion ("a local-only account can fully use the product with zero network calls to Drive; export/import round-trips correctly") is now mechanically true but not yet meaningfully exercised end-to-end.** The storage/backup infrastructure has zero Drive calls by construction, and export/import round-trips correctly against whatever is in `IndexedDB` — but no feature anywhere in the product yet _writes_ a real envelope (scanning/exam persistence doesn't exist for either account type — `M3-006` Drive CRUD, `M3-007` roster, `M3-008` results table are all still open `M3` tasks). The round-trip is proven against synthetic test envelopes, not a real exam result. This isn't a shortfall of this task specifically — there's nothing to persist yet, for any account type — but it's worth being precise about rather than implying more end-to-end coverage than exists.

## Part 1: email + OTP authentication (PR #48, merged)

The founder's directive, quoted in full, and everything built against it:

> "Decision: local-only accounts authenticate via passwordless email + OTP... Add an `auth_provider` column to `users`... Add a short-lived OTP table/mechanism... Session creation must converge to the same session mechanism regardless of which provider authenticated the user... Out of scope for now, but worth a one-line note in the ADR: a local-only account may later want to 'upgrade' to connect Google/Drive... Please document this as a new ADR... and proceed with implementation as part of M3."

**What was built:** `users.auth_provider` (`'google' | 'email_otp'`, deliberately independent of `auth_mode` — see `ADR-0018`'s "Future: account linking"); a new `email_otp_codes` table with its own purpose-scoped RLS lookup GUC (`app.otp_email_lookup`, same pattern as `M3-001`'s `google_sub_lookup`); `auth/email-otp.ts` (`requestEmailOtp`/`verifyEmailOtp`); `email/email-otp-email.ts`; `routes/email-otp.ts` (`POST /auth/email-otp/{request,verify}`, rate-limited via `@fastify/rate-limit`, converging on the same `createSession` the Google OAuth callback uses); `docs/ADR/0018-local-only-mode-email-otp-authentication.md`.

**Key decisions:** `requestEmailOtp` never touches `users` (no enumeration signal — account lookup/creation is deferred entirely to a successful `verifyEmailOtp`); SHA-256 hashing of codes at rest is defense-in-depth, not the real security boundary (that's the 5-attempt cap + 10-minute expiry + rate limiting); a new request invalidates every prior outstanding code for that email; an email already registered under a different provider gets `wrong_provider`, never a silent link/duplicate; rate limits (5 req/15min request, 10 req/15min verify) registered with `global: false` so this doesn't retroactively rate-limit every existing route; the OTP route's own email-sending uses the restricted `app_user` connection, matching every other request handler; `BuildAppOptions.emailSender` is optional to avoid rippling into every pre-existing `buildApp()` test call site.

**How it was tested:** `email-otp.test.ts` (code hashing/invalidation/expiry/attempt-cap/single-use/wrong-provider/normalization, real Postgres), `email-otp-email.test.ts` (content, `ADR-0011` no-student-data pattern), `email-otp-routes.test.ts` (validation, no-enumeration response shape, session/CSRF cookie issuance matching the Google callback, real `429` enforcement). 6 pre-existing test files updated for the new required `authProvider` column.

## Part 2: local-only product feature (this PR)

The remaining scope from `M3-005`'s original row: `docs/ARCHITECTURE.md` §7 already specified the storage model precisely enough to build directly against — "the same JSON envelope is written to IndexedDB instead of Drive... 'Export backup file' downloads the raw envelope(s); 'Import backup file' restores them" — so no further founder input was needed here, unlike Part 1.

### What was built

**API:**

- `auth/account.ts` + `routes/account.ts` — `GET /account/me` returning `{ authMode }`. Separate from `routes/encryption.ts` (encryption-specific) and `routes/email-otp.ts` (pre-session handshake) on purpose; needed by both the warning banner and the settings backup card, both of which must render correctly whether or not encryption setup has completed.

**Web (`apps/web/`):**

- `lib/storage/local-envelope-store.ts` — a dumb, content-agnostic IndexedDB store (`put`/`get`/`delete`/`listByType`/`listAll`), keyed by `recordId`, indexed by `type`. Hand-rolled promisification of the native IndexedDB API rather than a third-party wrapper — four operations over one object store don't need one. Tested against `fake-indexeddb` (new pinned devDependency), not mocked — real IndexedDB semantics, no browser needed.
- `lib/storage/backup.ts` — `createBackupBlob` (export) and `restoreBackupFromFile` (import), both pure/framework-agnostic (the actual `URL.createObjectURL`/download trigger is the UI's job, matching `recovery-key-reveal-card.tsx`'s existing split). Import skips malformed individual entries and reports a count rather than aborting the whole restore — the same per-item-failure judgment `M2-009`'s batch import already established.
- `lib/api/account-client.ts`, `lib/api/email-otp-client.ts` — thin fetch wrappers matching `account-encryption-client.ts`'s existing pattern.
- `app/(app)/local-only-warning-banner.tsx` — the "persistent, unmissable" warning `FR-AUTH-06` requires. Deliberately has **no** dismiss control, unlike `RecoveryKeyReminderBanner` — a standing data-loss risk that never stops being true shouldn't be hideable even for one page view, unlike a nudge the teacher can act on later. Wired into `(app)/layout.tsx` alongside the existing Recovery Key banner.
- `app/(app)/settings/backup-card.tsx` — Export/Import buttons, rendered in `/settings` for local-only accounts across every non-error/non-loading state (`needs-setup`, `setup-complete`, `can-change-passphrase`) — per `FR-AUTH-06`'s literal "available from the first session," not gated behind encryption setup completing, since neither operation touches the master key.
- `app/signin/page.tsx` + `signin-client.tsx` — the product's **first real sign-in entry point**: until this, the only "sign in" link anywhere was a small settings-page fallback for an already-lapsed session (confirmed by grep before building — no other file referenced `/auth/google/start` at all). Offers "Continue with Google" (a real `<a href>` to the API's OAuth start, since that's cross-origin) or local-only email+OTP (email → code → redirect to `/settings`, the same landing spot the OAuth callback already uses). `(marketing)/page.tsx` now links here instead of being a dead-end placeholder.

### Key decisions

- **The IndexedDB envelope's own encrypted-payload shape is deliberately left unspecified by this module** — see Flag 2 above. `StoredEnvelope` only requires `schemaVersion`/`type`/`recordId`; everything else is an open payload the store never reads.
- **`listEnvelopesByType` is included even though nothing in this task calls it** (only `listAllEnvelopes`, for export, is actually exercised yet). Justified as cheap-now/expensive-later: an IndexedDB index has to be declared at store-creation time (`db.createObjectStore`'s `onupgradeneeded`); adding one after the fact needs a version-bump migration. Every future feature reading local-only data (results by exam, rosters, etc.) will want to filter by `type`, so this is building the access pattern that's already visible, not a speculative abstraction.
- **The Backup card renders regardless of encryption-setup status** (see "What was built") — a deliberate reading of "available from the first session" as literal, not "available once setup completes."
- **`window.location.href` (a real navigation), not `next/navigation`'s `useRouter`, for the post-verify redirect to `/settings`.** No existing code in this app uses client-side routing (`grep` confirmed zero hits for `useRouter`/`next/navigation`), and a full page load is arguably the safer choice for a just-authenticated transition into the encryption-setup flow — no leftover component state or in-memory sign-in-form data survives into the next page. Caught a real test gap from this choice, not a production bug: jsdom's `Location` object doesn't perform navigation and leaves `href` unchanged on assignment (only logs a warning) — `signin-client.test.tsx` swaps in a plain mock object for `window.location` to observe the assignment the component actually makes, rather than weakening the assertion.
- **`requestEmailOtp`'s non-200 failure modes are not distinguished in `email-otp-client.ts`** (unlike `verifyEmailOtp`, which does distinguish `invalid_code`/`expired`/`too_many_attempts`/`wrong_provider`) — there's no realistic case where a well-formed email 400s, so a single generic "could not send a code" message covers it without over-building error-state UI for outcomes that can't actually occur.

### How it was tested

- **`local-envelope-store.test.ts`** (`fake-indexeddb`): round-trip by `recordId`; missing-key returns `undefined`; overwrite semantics; delete (including deleting a nonexistent key as a no-op); `listAllEnvelopes` vs `listEnvelopesByType` filtering, including an empty-type case.
- **`backup.test.ts`**: empty-store export shape; export includes every stored envelope exactly; import restores valid entries and skips malformed ones individually (counted, not aborting); import upserts (safe to run twice); invalid JSON and wrong-shape JSON both throw a clear, distinct error.
- **`account-client.test.ts`**: credentials included, non-OK throws.
- **`local-only-warning-banner.test.tsx`**: renders nothing while loading/on fetch failure/for a Google account; shows the warning with a link to `/settings#backup` for a local-only account; asserts **no** button/dismiss control exists — the deliberate difference from the Recovery Key banner.
- **`backup-card.test.tsx`**: export creates an object URL and revokes it; export failure shows an error; import reports restored/skipped counts; import failure shows the specific thrown message.
- **`settings-client.test.tsx`** (existing suite, re-verified): unaffected by the new independent `authMode` fetch — the effect is soft-fail (`.catch(() => {})`), verified by the existing suite still passing unchanged.
- **`email-otp-client.test.ts`**: request/verify wrappers' request shape, credentials, and outcome-vs-throw split.
- **`signin-client.test.tsx`**: choice screen shows both paths; local-only path requests a code and advances; request failure shows an error; successful verify redirects to `/settings`; `invalid_code` and `wrong_provider` outcomes show their distinct messages; "use a different email" and "back" navigation both work.
- **Full-suite regression**: `npm run ci` (format + lint + typecheck + test, both workspaces) green against real Postgres — 21 API test files/120 tests, 43 web test files/405 tests, nothing skipped.
