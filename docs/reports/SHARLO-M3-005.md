# SHARLO-M3-005 — Local-only mode: auth mechanism (email + OTP)

**Status: partial.** This task's original description (`docs/TASKS.md`: "IndexedDB storage path, persistent data-loss-risk warning, Export/Import backup file") assumed an account/session mechanism for local-only teachers already existed. It doesn't — every mechanism built through `M3-004` is Google-OAuth-specific. This report covers the auth-mechanism prerequisite the founder resolved and directed be built as part of `M3`: passwordless email + OTP sign-in, documented in new `ADR-0018`, fully implemented and tested. The IndexedDB storage path, warning banner, Export/Import, and local-only signup UI — `M3-005`'s original scope — remain open; see "Deviations" and "Current status" below.

## Flags

1. **A genuine architectural gap, stopped on rather than guessed through.** Starting this task surfaced that `FR-AUTH-06` (local-only mode) has no way for a teacher to authenticate at all: `users.email` is `NOT NULL UNIQUE`, but nothing populates it or proves control of it for an account with no Google identity, and every session-issuing code path (`routes/auth.ts`'s OAuth callback) is reached only at the end of the Google handshake. This is exactly the "scope seems ambiguous... or a real prerequisite not captured as a dependency" stop condition CLAUDE.md names — not a case where guessing a reasonable-looking design and moving on would have been appropriate, since the wrong choice here (e.g., a client-only fake identity, or an unauthenticated local-only account) would have meant rebuilding real account/billing infrastructure later. Flagged via `AskUserQuestion` with a reasoned recommendation as the first option; the founder's response (quoted in full below) is the authoritative spec this report documents building, not a starting point that was then reinterpreted:

   > "Decision: local-only accounts authenticate via passwordless email + OTP... Add an `auth_provider` column to `users`... Add a short-lived OTP table/mechanism... Session creation must converge to the same session mechanism regardless of which provider authenticated the user... Out of scope for now, but worth a one-line note in the ADR: a local-only account may later want to 'upgrade' to connect Google/Drive... Please document this as a new ADR... and proceed with implementation as part of M3."

   Every structural decision below (the `auth_provider`/`auth_mode` split, the OTP table shape, rate-limiting requirement, session convergence, and explicitly not building account-linking yet) traces directly to this message, not to independent judgment. Where a real choice was still left open (hash algorithm, exact rate-limit thresholds, code digit count, enumeration-resistance approach, connection privilege level), that's called out under "Key decisions" as this task's own judgment, made within the founder's frame rather than in place of it.

2. **`M3-005` is not fully closed by this report.** The task's original acceptance criterion ("a local-only account can fully use the product with zero network calls to Drive; export/import round-trips correctly") is untouched — no IndexedDB storage adapter, warning banner, export/import, or local-only signup UI exists yet. `docs/TASKS.md`'s `M3-005` row is updated to reflect this split explicitly (same pattern `M3-004` used for its own onboarding-UX/reminder-cadence split), not marked done.
3. **Adding `users.auth_provider` as `NOT NULL` with no default required updating six pre-existing test files** that insert `users` rows directly (bypassing the app's own `findOrCreateUser*` helpers): `csrf-protection.test.ts`, `encryption-routes.test.ts`, `recovery-key-reminders.test.ts`, `rls.test.ts`, `session.test.ts`, `templates-rls.test.ts`. Each got `authProvider: 'google'` added alongside its existing `authMode: 'google'` fixture value — mechanical, expected, verified by re-running the full suite afterward, not glossed over.

## What was built

**Schema (`apps/api/src/db/schema.ts`, migration `0006_old_champions.sql`):**

- `users.auth_provider` (`'google' | 'email_otp'`, `NOT NULL`) — how an account authenticates, independent of the existing `auth_mode` (where its student data lives). Deliberately kept as a separate column rather than merged into `auth_mode` or inferred from `google_sub IS NULL` — see ADR-0018's "Future: account linking."
- `users_select_by_email_lookup` — a new permissive SELECT policy on `users`, scoped against a new `app.email_lookup` GUC, ORed with the table's existing self-access and `google_sub_lookup` policies. Same chicken-and-egg shape `M3-001`'s `google_sub_lookup` policy solved: verifying an OTP has to check "does an account for this email already exist" before any user id exists to scope the query with.
- `email_otp_codes` (new table, RLS-enabled): `email`, `code_hash`, `expires_at`, `attempts`, `consumed_at`, `created_at`. One permissive `ALL` policy (`email_otp_codes_by_email_lookup`) scoped against a new `app.otp_email_lookup` GUC — not a meaningful access-control boundary by itself (anyone can claim any email at this layer), the same as the other lookup GUCs aren't; the real protection is expiry + attempts + rate limiting.

**API (`apps/api/src/`):**

- `db/client.ts` — `withEmailLookupContext`, `withOtpEmailLookupContext`, the same `withGucContext`-based pattern as every other purpose-scoped lookup.
- `auth/email-otp.ts` — `requestEmailOtp` (mints a 6-digit code, hashes it, deletes any prior outstanding code for the email, emails it — never touches `users`) and `verifyEmailOtp` (checks the code against hash/expiry/attempt-cap, and only on success finds-or-creates the `users` row and returns a `userId`).
- `email/email-otp-email.ts` — `buildEmailOtpMessage`, account-level content only (`ADR-0011`), same as every other transactional email this app sends.
- `routes/email-otp.ts` — `POST /auth/email-otp/request` and `POST /auth/email-otp/verify`, both rate-limited via `@fastify/rate-limit`. Verify calls the exact same `createSession` the Google OAuth callback calls and sets the identical `sharlo_session`/`sharlo_csrf` cookies.
- `app.ts` — registers `@fastify/rate-limit` (`global: false`) and the new routes; `BuildAppOptions.emailSender` made optional (see "Key decisions").
- `index.ts` — constructs one `appDb` connection, used both for `buildApp`'s `db` and a `ResendEmailSender(appDb)` passed as `emailSender` (the restricted, request-scoped connection — matching every other request handler, not the scheduler's privileged one).
- `db/testing/provision-app-role.ts` — grants `app_user` `SELECT, INSERT, UPDATE, DELETE` on `email_otp_codes`.

**Docs:** `docs/ADR/0018-local-only-mode-email-otp-authentication.md` (new), `docs/TASKS.md` (`M3-005` row split), `docs/ARCHITECTURE.md` (§6 schema sketch, §9 auth narrative, §15 resolution log item 17), `CLAUDE.md` (decisions log).

## Key decisions

Judgment calls made within the founder's spec, not in place of it:

- **`requestEmailOtp` never touches the `users` table at all.** The founder's message described `/request` as creating-or-reusing a user row; building it, the enumeration risk of doing that (an attacker learns "this email has an account" from response timing/side effects even with an identical response body) was judged worth closing by deferring all `users` interaction to `/verify`, after inbox control is proven. `/request`'s behavior and response are now bit-for-bit identical whether or not the email has an account. (ADR-0018 was corrected to describe this accurately — its first draft still said `/request` touches `users`, fixed before this report.)
- **SHA-256 for `code_hash`, explicitly not the real security boundary.** A 6-digit code is a 1-in-a-million space regardless of hash strength; the hash is defense-in-depth against a database read/backup leak, not brute-force resistance. The real protection is the 5-attempt cap, 10-minute expiry, and rate limiting — documented as such in both the ADR and inline comments, so a future session doesn't "upgrade" to bcrypt/Argon2 thinking it closes a gap it doesn't.
- **Re-requesting a code invalidates every prior outstanding one** (deletes unconsumed rows for that email before inserting the new one) — only the most-recently-sent code is ever valid. Without this, a teacher requesting several codes in a row (e.g., retrying after a slow email) would let an attacker's attempt budget spread across multiple live rows instead of being capped against the one that matters.
- **An email already registered under a different `auth_provider` returns `wrong_provider`, not a silent link or a duplicate account.** Safe to reveal (the caller just proved inbox control by entering a valid code), and correct per the founder's explicit "don't build the linking flow now" instruction — `wrong_provider` is the honest answer without building the feature that would resolve it.
- **`@fastify/rate-limit`, verified from its installed `.d.ts`, not memory** — 5 req/15min on `/request`, 10 req/15min on `/verify` (looser, since a real user mistyping a code needs a few tries; the per-code attempt cap is the actual brute-force defense). Registered with `global: false` so this applies only to the two new routes — a blanket rate-limiting pass across every existing endpoint is real, separate `M7` hardening work, flagged rather than silently expanded into this task.
- **The OTP route's own email-sending uses the restricted `app_user` connection**, not the privileged one `M3-004`'s scheduler uses — matching every other request handler's privilege level. `integration_credentials` isn't RLS-scoped (`M0-010`) and `app_user` already has `SELECT` on it, so both connection types can read the Resend credential equally; the choice is about matching the code path's actual privilege level (a per-request operation), not a technical requirement of the read itself.
- **`BuildAppOptions.emailSender` made optional**, unlike the schema's `authProvider` column. Forcing every pre-existing test that calls `buildApp()` to pass a sender would have been a wide, unnecessary ripple for a parameter most of those tests don't care about; a missing sender throws loudly (`NO_EMAIL_SENDER_CONFIGURED`) the moment something actually tries to send, rather than silently no-op-ing.
- **Email normalized (trimmed, lowercased) at both `email-otp.ts` entry points** — prevents `Teacher@Example.com` and `teacher@example.com` being treated as different accounts or different OTP rows.

## Deviations from the original task description

`M3-005`'s original scope (IndexedDB storage, warning banner, export/import) is unchanged and un-started — this report doesn't claim otherwise. The deviation is additive: an auth-mechanism prerequisite the original task description didn't anticipate, because the SRS/ARCHITECTURE docs describe local-only mode's _data_ boundary (§2's (A)/(B) split) without specifying how a local-only account authenticates for the (B)-side (billing/entitlement/usage-counters) that still lives in Postgres regardless of where student data lives. Same pattern as `M3-004`'s onboarding-UX/reminder-cadence split: the founder was asked, gave an explicit instruction, and the row in `docs/TASKS.md` is updated to show exactly what's done and what remains, rather than silently narrowing or silently expanding scope.

## How it was tested

- **`email-otp.ts` logic** (`apps/api/test/email-otp.test.ts`, real Postgres, restricted `app_user` connection): sends a 6-digit code and stores only its hash; never creates a `users` row on request alone; rejects verification when no code was ever requested; a new request invalidates the prior code; a code is rejected once expired (backdated via direct SQL, same pattern `M3-004`'s reminder tests use); 5 wrong attempts lock out the 6th try even with the correct code; first successful verification creates a `local_only`/`email_otp` user; a second sign-in finds the same user rather than duplicating; a code can't be replayed after a successful verify; an email already registered under `google` gets `wrong_provider` without creating a duplicate; email case/whitespace normalizes consistently between request and verify.
- **Email content** (`apps/api/test/email-otp-email.test.ts`): addressed to the right recipient, includes the code, states the 10-minute expiry, never mentions students/rolls/classes/exams (`ADR-0011`'s pattern), provides both html and text bodies.
- **HTTP routes** (`apps/api/test/email-otp-routes.test.ts`, real Postgres, `app.inject`): malformed email/code rejected with 400; a brand-new email and an already-registered email get the identical 200/`{ok:true}` response shape (no enumeration signal); a wrong code returns 400 with its outcome; a successful verify sets the same `sharlo_session`/`sharlo_csrf` cookies the Google OAuth callback sets, backed by a real row in `sessions`; both routes 429 after their respective rate limits are exceeded (5 for request, 10 for verify) — confirmed empirically against the real `@fastify/rate-limit` plugin, not assumed from its docs.
- **Full-suite regression**: all 6 pre-existing test files touched by the new `authProvider` column re-verified passing. Full `npm run ci` (format + lint + typecheck + test, both `api` and `web` workspaces) green against a real local Postgres instance — 20 API test files/117 tests, 36 web test files/366 tests, nothing skipped.
