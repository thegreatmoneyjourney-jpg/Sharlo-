# SHARLO-M3-018 — Teacher-removal continuity handling

## Flags

**A real research finding that weakens `ADR-0010`'s own stated folder-path limitation, surfaced prominently rather than quietly built around.** `ADR-0010`'s "Known limitation" (Consequences section) frames the folder-path (personal-Gmail-admin) continuity guarantee as best-effort with a _narrow window_ of risk: "a teacher removed before any ownership-transfer step runs, or one that fails." While building this task, research (via web search — this sandbox cannot reach `developers.google.com` directly, the same access limitation `M1-011`/`M3-001`/`M3-006` already carry for their own real-infrastructure gaps) found a more structural problem than "narrow window" implies:

- Google Drive's documented ownership-transfer mechanism is **owner-initiated** — the file's _current_ owner calls the API to hand ownership to someone else.
- Even then, it typically requires the **recipient's separate consent/acceptance**. Same-domain programmatic transfers have been observed returning `403 Consent is required to transfer ownership` even when both accounts are genuinely cooperating.
- The call shape this task's `attemptOwnershipTransferForDepartingTeacher` actually has available to it — the **admin** (a non-owner, holding only an inherited Editor permission via the shared folder) attempting to upgrade their own existing permission entry to `role: owner` — is the _only_ version of this call our app's admin session could ever attempt unilaterally. There is real reason to doubt Drive honors a non-owner-initiated self-upgrade at all.

If it doesn't, this mechanism fails by construction in exactly the adversarial/uncooperative-departing-teacher scenario it exists to mitigate — not just in an occasional edge case as "narrow window" suggests.

**Not verified against a real Google Drive account** — this project has none configured anywhere, sandbox or CI, the same category of gap `M1-011` (real-device scanning), `M3-001` (real iOS Safari OAuth), and `M3-006` (real Drive account) already carry. Every test here mocks the Drive REST API.

**Decision made (reconcile-and-build, not escalate-and-block):** built the mechanism faithfully anyway, because (a) it's the only mechanism available to an admin acting alone, and (b) `ADR-0010` already frames this path as best-effort, never guaranteed, so building the best currently-available attempt is consistent with the Accepted decision rather than a deviation from it. This is not a fresh `AskUserQuestion`-style escalation — there's no alternative design choice for me to present, only a research finding about how well an already-approved mechanism actually works, which is exactly what `ADR-0010`'s own addendum pattern (items 1–4) exists to capture. Every outcome (success or failure) is surfaced to the admin per file, never assumed; the UI's "best-effort continuity guarantee" wording appears only when a transfer actually fails, never as a blanket claim.

**Recommendation left for the founder** (recorded in `ADR-0010`'s addendum, item 5, not just here): treat the folder path's continuity guarantee as weaker than "narrow window" until verified against a real Drive account (ideally two real accounts, one deliberately non-cooperating, to test the worst case this mitigation targets). If the self-upgrade call turns out to fail unconditionally for a non-owner, the real fix is either (a) accepting that the folder-path guarantee is effectively "none, if the teacher doesn't cooperate" in product copy and steering even harder toward the Workspace/Shared-Drive path, or (b) a different mitigation entirely (e.g., requiring the departing teacher's own session to run the transfer _before_ access is revoked — which has its own obvious problem in a genuinely adversarial departure, where the teacher has no incentive to cooperate).

No other scope ambiguity, contradiction, or missing prerequisite was found in this task.

## What was built

**Backend (`apps/api`):**

- `removeTeacherFromSchool(db, adminUserId, memberId)` (`apps/api/src/auth/school-members.ts`) — deletes a `school_members` row. Relies entirely on the existing `school_members_admin_manages_own_school` RLS policy (`for: 'all'`, already covers DELETE) to scope the delete to schools the caller admins; a `memberId` under a school the caller doesn't own, or that doesn't exist, deletes zero rows. `.returning()` (not a driver-specific row-count field) distinguishes `'removed'` from `'member_not_found'`.
- `DELETE /schools/:id/members/:memberId` (`apps/api/src/routes/schools.ts`) — session-authenticated, CSRF-protected (the existing global double-submit hook), returns `204` on removal or `404 {error: 'member_not_found'}` otherwise.
- `GET /account/me` extended to return the signed-in user's own `email` alongside `authMode` (`apps/api/src/auth/account.ts`'s `AccountInfo`/`getAccountInfo`) — a genuine prerequisite gap this task found: nothing before now exposed a user's own email to their own client, but the ownership-transfer step needs the _admin's_ email to identify which of a file's several inherited Drive permissions belongs to the admin (as opposed to any other teacher sharing the same folder).

**Web (`apps/web`):**

- `lib/drive/transfer-teacher-owned-files.ts` — `attemptOwnershipTransferForDepartingTeacher(folderId, teacherEmail, adminEmail)`. Lists files the departing teacher owns inside the folder (`'<email>' in owners` query), then for each file attempts to upgrade the admin's own existing permission entry (matched by `adminEmail` against the file's `permissions[].emailAddress`) to `role: 'owner'` with `transferOwnership=true`. Never throws — every outcome (`'transferred'` or `'transfer_failed'` with a specific error) is returned per file. Carries the full feasibility-research doc comment described above.
- `lib/drive/revoke-school-container-access.ts` — `revokeSchoolContainerAccess(containerId, teacherEmail)`. Finds the teacher's permission on the container by email (`permissions.list`, filtered client-side), then deletes it. A no-op (not an error) if no such permission exists — covers both "never completed the Picker step" and "already removed."
- `lib/drive/remove-teacher-from-school.ts` — `removeTeacherFromSchool(school, member)`, the orchestration function tying the above together in `ADR-0010`'s required order: attempt transfer (folder path only; never attempted on the Shared Drive path, matching the ADR's own "for the fallback (folder) path specifically" wording) → revoke access → delete the membership row (`submitRemoveTeacher`, new in `lib/api/schools-client.ts`). If revocation throws, the function throws too and the membership row is deliberately **not** deleted, so a retry still has the context (teacher email, Drive location) it needs.
- `school-members-panel.tsx` — a "Remove" button per teacher, behind a two-step confirm (click "Remove" → "Confirm remove" / "Cancel") given this is a materially harder-to-reverse action than the existing per-exam "Remove student" row-delete (which is just in-memory grid state). Surfaces every outcome: the row disappears from the list on success; a specific amber notice appears if any file's ownership transfer failed, naming the file and explaining the weaker-guarantee reason; a specific error appears (teacher stays listed) if the whole operation throws.

## Key decisions

1. **Transfer → revoke → delete ordering is load-bearing, not arbitrary.** Revoking the Drive permission first would strip the admin's own inherited permission on the teacher's files before the self-upgrade attempt could use it — `ADR-0010`'s own "Teacher removal" section states this ordering explicitly, and the orchestration function's tests assert the call order directly.
2. **The membership row is deleted last, and only on confirmed revocation success.** If Drive revocation fails (a real network/API error, not "nothing to revoke"), the row is kept so the admin's next retry attempt still has the teacher's email and the school's Drive location to work from — deleting it regardless would silently lose that context on a failure that's likely transient.
3. **A two-step UI confirm, not a `window.confirm()` native dialog and not a silent single click.** No precedent either way existed in this codebase (the one other destructive row-delete, `results-grid.tsx`'s "Remove student," is a single click, but that's reversible in-memory grid state — this isn't). Chose a plain inline two-click pattern consistent with this codebase's no-modal-library style, proportionate to the action's actual stakes.
4. **`GET /account/me`'s new `email` field reuses the existing endpoint rather than adding a new one.** `AccountInfo` already exists specifically to expose small, non-secret facts about the signed-in user's own account to their own client; an email the user already knows is squarely that category, and a second endpoint for one more field would be needless surface area.

## Deviations from the original task description

None in scope. The one deviation worth naming is in emphasis, not scope: the task's own done-when criterion asked for a test that "logs/surfaces [the ownership-transfer outcome] rather than failing silently," which is built and tested — but the research finding above goes further than that criterion asked for, by questioning whether the underlying mechanism can succeed at all without the departing teacher's cooperation. This isn't scope creep (nothing extra was built because of it) — it's an honest account of what was learned while building the thing that was actually asked for, flagged per this repo's stop-conditions discipline rather than silently noted only in a code comment.

- **Full typecheck and lint** (`npx tsc --noEmit`, `npx eslint`) run clean on every new/edited file in both `apps/web` and `apps/api`.
