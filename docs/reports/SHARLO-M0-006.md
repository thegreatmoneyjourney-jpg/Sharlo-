# Report: SHARLO-M0-006 — Drizzle schema skeleton + RLS cross-tenant proof

**Status: done — CI found a real bug in the RLS policy on the first attempt, fixed, re-verifying now.**

## Flags

1. **CI's first run (PR #3, attempt 1) failed, and it was a genuine bug, not a flake — worth reading even though it's now fixed.** 2 of 3 RLS assertions passed on the first try (tenant A reads their own row; tenant A is blocked from tenant B's row) — the core mechanism works. The third ("unscoped query sees zero rows") failed with `invalid input syntax for type uuid: ""`, not the expected zero-rows result. Root cause: the original policy used `current_setting('app.current_user_id', true)::uuid` on the assumption that "never set" always reads back as Postgres `NULL`. That's true for a genuinely fresh connection, but **not** for a _pooled_ connection that previously ran a request inside a `SET LOCAL`-scoped transaction — once a custom GUC has been touched at all on a connection, Postgres resets it to an **empty string**, not `NULL`, when that transaction ends. Casting `''` straight to `::uuid` throws a hard Postgres error instead of safely denying. This is exactly the situation the real Fastify app will be in (connection-pooled, per `ARCHITECTURE.md` §9), so this wasn't a test artifact — it was a real latent robustness gap in the policy itself, and the fix is in the policy, not the test: `nullif(current_setting('app.current_user_id', true), '')::uuid` normalizes both "never set" and "reset-to-empty-on-a-reused-connection" down to `NULL` before the cast, so both fail closed cleanly. Regenerated the migration from the corrected schema (this project's first migration has never been applied anywhere but ephemeral CI containers, so regenerating `0000` instead of stacking a `0001` fixup keeps history clean while that's still true). Full reasoning is now a comment in `schema.ts` itself, not just this report, since it's exactly the kind of non-obvious constraint a future change to this policy could easily reintroduce.
2. **Could not run or verify any of this locally.** This sandbox has the Docker CLI installed but no reachable daemon (`docker ps` fails with "no such file or directory" on the socket), and no local Postgres server binary either. Every other piece of work this session (lint, typecheck, builds, the health-endpoint test) was verified by actually running it — this is the one exception. What I did instead: designed the test to `describe.skipIf` cleanly when `DATABASE_URL`/`APP_DATABASE_URL` aren't set (confirmed locally: it skips, doesn't fail, doesn't silently pass), and wired a real Postgres service container into CI so the suite runs for real there. That CI run is what caught Flag 1 above — a concrete demonstration of exactly why this needed real verification rather than "the design reads correctly to me."
3. **A real, separate `npm audit` finding surfaced while installing `drizzle-kit`**: 4 moderate vulnerabilities, all in `@esbuild-kit/core-utils`/`@esbuild-kit/esm-loader` (deprecated packages, "merged into tsx") pulled in transitively by `drizzle-kit` 0.19.0–1.0.0-beta's own tooling. `npm audit fix --force` "fixes" this by **downgrading drizzle-kit to 0.18.1** — 13 minor versions back, before the vulnerable chain was even introduced. I did not take that fix: the advisory itself ("esbuild enables any website to send any requests to the development server and read the response") only matters if you're actively running `esbuild serve` and browsing a malicious site at the same time — it's about esbuild's own dev server, not our Next.js or Fastify dev servers, and `drizzle-kit` is a one-shot CLI (`generate`/`migrate`), not a persistent server. Downgrading 13 versions for a low-practical-risk advisory in a dev-only CLI's internal tooling felt like a worse trade than leaving it, especially with Dependabot (M0-004) now watching for a real forward fix. Flagging this explicitly as a judgment call rather than a silent skip, and it'll be visible to Dependabot going forward regardless.

## What was built

- `apps/api/src/db/schema.ts`: the `users` table per `ARCHITECTURE.md` §6 (id, email, `google_sub`, auth mode, account type, wrapped-key ciphertext fields, KDF params, the Recovery Key reminder timestamps from the ADR-0005 addendum, `schema_version`, timestamps) — deliberately the M0-006 proof-of-concept slice, not the full account schema. RLS enabled via Drizzle's `pgPolicy`/`.enableRLS()` API (current as of the installed `drizzle-orm` 0.45.3 — checked the actual shipped type definitions before writing this, same discipline as the Next.js version check in M0-002, rather than assume an older syntax). Policy: `id = current_setting('app.current_user_id', true)::uuid`, with the `true` (missing-ok) flag specifically so an unscoped connection gets `NULL`, and `id = NULL` is never true — fails closed, per ADR-0008, and the test proves this rather than just asserting it (see below).
- A generated migration (`drizzle-kit generate`) creating the table, enabling RLS, and creating the policy — reviewed the actual SQL output rather than trusting the generator blindly; it's correct.
- **The restricted role is provisioned separately from the migration**, deliberately: Postgres requires the role named in `CREATE POLICY ... TO "app_user"` to already exist, so `apps/api/src/db/testing/provision-app-role.ts` creates it (idempotent, `NOSUPERUSER NOBYPASSRLS` explicit) _before_ migrations run, and grants table privileges _after_ the table exists — RLS controls row visibility, but the role separately needs an ordinary `GRANT` to touch the table at all, which is an easy thing to forget and get a confusing "permission denied" that looks like an RLS bug but isn't. `apps/api/src/db/migrate.ts` orchestrates the correct order (role → migrate → grant) and is also the `db:migrate` script for local/future use.
- `apps/api/src/db/client.ts`: `withTenantContext()`, matching `ARCHITECTURE.md` §8's description — `SET LOCAL` (not `SET`) inside a transaction, so the tenant claim can never leak across a pooled connection into an unrelated request.
- `apps/api/test/rls.test.ts`: three real assertions, not one — tenant A can read their own row (positive case, so the test can't pass merely because everything is broken), tenant A cannot read tenant B's row by direct id lookup, and a connection with no tenant context set at all sees zero rows. That third one is the "fails closed" property from ADR-0008 specifically, not just implied by the other two.
- CI: added a `postgres:16-alpine` service container to `.github/workflows/ci.yml` with a health check, and the `DATABASE_URL`/`APP_DATABASE_URL`/`APP_DB_ROLE_PASSWORD` env vars the test needs (dev-only throwaway credentials against an ephemeral, CI-only database — never used anywhere else).

## Key decisions

- **`users`' own `id` is the tenant identifier for this table's policy** — a deliberate special case, called out in a comment in `schema.ts` itself: every other tenant-scoped table added later (subscriptions, usage counters, templates) will have a separate `user_id` FK column and its policy compares _that_, not its own `id`. Worth a comment specifically because copying this table's exact predicate onto the next table would be a subtle, easy-to-miss bug.
- Role/password provisioning kept **out of** Drizzle's schema-migration files on purpose — migrations are schema-versioned and reviewed as such; role and password provisioning is an infra/deploy concern that in a real environment comes from a secret, not a committed value. `.env.example` documents this distinction explicitly rather than presenting one flat list of variables.
- Test data cleanup (`afterAll`) deletes the two seeded rows explicitly rather than relying on transaction rollback, since the migration/role-provisioning step needs to have actually committed for the RLS behavior to be real (running everything inside one giant uncommitted transaction would test something subtly different from what production actually does).
