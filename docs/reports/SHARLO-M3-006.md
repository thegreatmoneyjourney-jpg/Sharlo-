# SHARLO-M3-006 — Drive file CRUD (browser-direct)

**Status: done.** Builds the browser-direct Google Drive read/write path `ADR-0004`/`ARCHITECTURE.md` §7 already specified, and — per the founder's explicit Addendum 8 instruction — resolves the envelope-encoding discrepancy `SHARLO-M3-005` flagged rather than leaving it open for a later task to rediscover.

## Flags

1. **Envelope-encoding resolution (Addendum 8's explicit ask): the real, already-tested crypto (`apps/web/lib/crypto/aes-gcm.ts`) was made authoritative, not `ARCHITECTURE.md` §7's old illustrative JSON.** §7 previously showed the encrypted payload split into three fields (`iv`, `ciphertext`, `authTag`, each base64). This task's `envelope-crypto.ts` instead produces/consumes **one field**: `ciphertext`, hex-encoded, holding `aesGcmEncrypt`'s real combined-blob output (`iv || ciphertext+authTag` — WebCrypto appends the auth tag to the ciphertext automatically; `aesGcmDecrypt` expects that same combined shape back). Why the doc lost and the code won: `aes-gcm.ts` was already built, tested, and in production use for master-key wrapping since `M3-003` — introducing a second encryption code path just to match an illustration nothing had implemented yet would have meant two AES-GCM call shapes in the same codebase for no functional reason. Hex (not base64, which the old illustration used) matches every other encoded byte value already in `lib/crypto/` (`encoding.ts`'s own stated reasoning — no padding, no URL-unsafe characters — applies identically to an envelope's ciphertext). `ARCHITECTURE.md` §7 is updated to show the real shape; `docs/TASKS.md`'s `M3-006` row and `CLAUDE.md`'s decisions log both point here as the resolution, per Addendum 8's explicit "confirm in that task's report which of the two was authoritative and why" instruction.
2. **Not verified against a real Google Drive account or real Google OAuth credentials.** This project has never had real Google OAuth credentials configured anywhere — not in this sandbox, not (as far as this session can tell) in CI. Every test in this task mocks Google's token-refresh endpoint and the Drive REST API; nothing here has actually created a file in a real Drive, actually queried it back by `appProperties`, or exercised Google's real error responses (rate limits, `invalid_grant` on a revoked token, Drive storage-quota errors, etc.). This is the same category of limitation `M1-011` (real-device scanning accuracy) and `M3-001`'s report (real iOS Safari popup behavior) already carry for this project — flagged the same way, not a new kind of gap. Whoever first runs this against a real teacher Google account (presumably once `M3-012`'s OAuth app verification and real credentials exist) should treat that as the actual end-to-end proof this report's own tests can't provide.
3. **List operations have a real, inherent per-file-fetch cost against Drive that IndexedDB doesn't have** (see "Key decisions" below) — not a bug, but worth surfacing prominently since a future list-heavy feature (`M3-008` results table, `M3-009` analytics) will inherit it for Drive-mode accounts specifically.

## What was built

**API (`apps/api/src/`):**

- `auth/google-oauth.ts` — added `refreshAccessToken`, matching `exchangeCodeForTokens`'s existing injectable-`fetch` shape.
- `auth/drive-access.ts` — `mintDriveAccessToken(db, userId, refreshAccessTokenImpl?)`: reads and decrypts the account's stored `googleRefreshTokenEncrypted`, reads the `google_oauth` client credentials via `credential-store.ts`, calls the refresh grant, returns `{accessToken, expiresInSeconds}`. Throws `NoGoogleRefreshTokenError` (no stored refresh token — e.g. a local-only account) or `GoogleTokenRefreshError` (the refresh call itself failed — e.g. revoked access) rather than letting either propagate as an opaque error.
- `routes/drive.ts` — `POST /account/drive-access-token`, session-authenticated, CSRF-protected via the existing global hook, maps the two error types above to `409`/`502` respectively.
- `app.ts` — registers the route with an injectable `refreshAccessToken` for tests, matching `googleOAuthClient`'s existing pattern.

**Web (`apps/web/`):**

- `lib/storage/envelope-crypto.ts` — `encryptEnvelope`/`decryptEnvelope`, the actual resolution described in Flag 1.
- `lib/api/drive-token-client.ts` — `getDriveAccessToken()`: calls the API above, caches the result **in memory only** (module-level state, never persisted), refreshes ~60 seconds before Google's own expiry, and de-duplicates concurrent callers into one in-flight mint rather than one each.
- `lib/storage/drive-envelope-store.ts` — `putEnvelope`/`getEnvelope`/`deleteEnvelope`/`listEnvelopesByType`/`listAllEnvelopes` implemented directly against Drive API v3 (`files.list` with an `appProperties` query, multipart create/update, `alt=media` content fetch, `DELETE`) — the same five-function shape `local-envelope-store.ts` already has.
- `lib/storage/envelope-store.ts` — the facade: `getEnvelopeStore()` resolves the account's `authMode` (via `GET /account/me`, cached for the page's lifetime) and returns the matching store, so `M3-007` onward never has to branch on account type itself.

## Key decisions

- **Envelope encoding — see Flag 1.** The single load-bearing decision this task was explicitly asked to make and document.
- **`appProperties` are metadata for querying only; the envelope itself lives in the file's content.** A `StoredEnvelope`'s `type`/`recordId`/`schemaVersion` are duplicated into Drive's `appProperties` (all Drive-required strings) purely so `files.list`'s `q` filter can find a file without downloading anything first — `getEnvelope`/`listEnvelopesByType`/`listAllEnvelopes` all reconstruct the actual envelope from the file's own `alt=media` content, never from `appProperties`, since `appProperties` doesn't (and shouldn't) carry the ciphertext.
- **Listing is `1 files.list call + N content fetches (parallel)`, not 1 call.** Drive's API has no "give me these 20 files' content in one response" outside its separate batch-request mechanism, which this task doesn't build — nothing in the codebase yet lists enough records for the extra round-trips to matter, and building batch support speculatively for a usage pattern that doesn't exist yet would be exactly the kind of premature complexity this project avoids elsewhere. Flagged clearly (Flag 3) so `M3-008`/`M3-009` know this going in rather than discovering it as a surprise performance regression.
- **The Drive access token is cached in memory only, on the client, with a proactive refresh margin.** Never written to `localStorage`/IndexedDB/a cookie — it's a live, real credential, and the whole point of minting it fresh per short window is that losing the cache (a page reload) costs one extra round-trip, not a security exposure. Concurrent callers sharing one in-flight mint (rather than each independently hitting `/account/drive-access-token`) is a small, directly-tested addition, not speculative — multiple envelope writes close together is a completely ordinary usage pattern for this product (e.g. saving several students' results in a batch), not a hypothetical.
- **`escapeDriveQueryValue` exists even though no current caller can trigger it.** Every `type`/`recordId` value passed into a Drive query today is either a UUID or one of this app's own fixed type-name strings, neither of which can contain a literal `'`. Escaping it anyway is one line, and query-string construction should never quietly assume its inputs are safe just because today's callers happen to be — the kind of defense-in-depth this project applies elsewhere (e.g. the OTP lookup GUCs' own "not a security boundary by itself, but still correct" framing) more than a speculative feature.
- **The access-token-minting endpoint is a `POST`, not a `GET`**, even though nothing about it changes server state — matching the reasoning `M3-004`'s own reminder-confirm endpoint used: it triggers a real external network call and returns a live credential, which is closer to "an action with a side effect" than a plain data read, and keeping it off `GET` means it's automatically covered by the existing CSRF double-submit hook without special-casing anything.

## How it was tested

- **`google-oauth.ts`'s `refreshAccessToken`**: covered indirectly through `drive-access.test.ts`'s injected mock (see below) — no standalone test file, matching `exchangeCodeForTokens`'s own precedent of being exercised through its real call sites' tests rather than in isolation.
- **`drive-access.test.ts`** (real Postgres): mints a token using the decrypted refresh token and stored `google_oauth` credentials; throws `NoGoogleRefreshTokenError` for an account with none stored; throws `GoogleTokenRefreshError` (not a raw error) when the refresh call itself fails.
- **`drive-routes.test.ts`** (real Postgres, `app.inject`): rejects no session (401) and a missing CSRF header (403); returns the minted token on success; maps both error types to their respective status codes (409, 502).
- **`envelope-crypto.test.ts`**: round-trips arbitrary content; produces the expected single-`ciphertext`-field shape (asserts `iv`/`authTag` are absent); never leaks plaintext into the envelope; fails cleanly (never partial output) on the wrong master key; rejects an envelope missing its `ciphertext` field.
- **`drive-token-client.test.ts`** (fake timers): mints and caches a token, sending credentials and the CSRF header; reuses the cache while comfortably valid; re-mints once within the refresh margin of expiry; shares one in-flight mint across concurrent callers rather than firing one each; throws clearly on a non-OK response.
- **`drive-envelope-store.test.ts`**: `putEnvelope` creates (POST, no fileId in the URL) when nothing matches, updates (PATCH, fileId in the URL) when something does — asserting the actual multipart body content and boundary structure, not just that a request was sent; `getEnvelope`/`deleteEnvelope` both correctly no-op (no second request) when nothing matches; `listEnvelopesByType`/`listAllEnvelopes` query correctly and fetch every match's content in parallel; a literal `'` in a query value is escaped; a non-OK Drive response throws with a clear message. A real bug was caught and fixed while writing these, not shipped: the test-only `_configureDriveEnvelopeStoreForTests` helper originally reset **both** injectable dependencies to their real defaults on every call, even when a test only meant to override one — a test setting `getAccessToken` in `beforeEach` and only `fetchImpl` per-test would silently lose the `beforeEach` value and fall through to a real (failing, in a test environment) network call. Fixed at the source (only override what's explicitly passed; a separate `_resetDriveEnvelopeStoreForTests` for the deliberate full-reset case), not patched around in the test file.
- **`envelope-store.test.ts`**: returns the local store for a `local_only` account, the Drive store for a `google` account, and caches the resolved `authMode` (a second call doesn't re-fetch).
- **Full-suite regression + `npm run ci`**: both workspaces green against real Postgres.
