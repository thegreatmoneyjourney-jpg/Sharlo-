## 🚩 Flags — read this section first

### 1. Found and fixed a real pdfjs-dist/browser compatibility bug — treated as blocking, not a test-environment quirk

While building this task's real-browser Playwright verification (see "How this was tested"), rendering a real PDF page through `pdfjs-dist` threw immediately:

```
TypeError: this[#methodPromises].getOrInsertComputed is not a function
    at #cacheSimpleMethod ... at WorkerTransport.getOptionalContentConfig ... at _PDFPageProxy.render
```

`Map.prototype.getOrInsertComputed`/`getOrInsert` is a very recent JS feature (the TC39 "Upsert" proposal). `pdfjs-dist` calls it unconditionally, in both its main-thread bundle and its worker bundle, with no feature-detection or fallback of its own — and this isn't specific to v6.3.289: checked back through every 5.x/6.x version currently published (as far back as 5.7.284), all of them call it the same way. Confirmed missing in two independent, fairly current runtimes while investigating — Chromium 141 (Playwright 1.56.1's bundled build) and Node 22.22.2 — so this isn't a stale-test-browser artifact; it's a real gap between what pdfjs-dist's whole recent version line assumes and what's actually available yet in widely-deployed browser engines. Given this app's own target users (teachers on a broad range of devices/browsers, not a controlled fleet of latest-Chrome desktops), shipping the PDF batch-import path without a fix would have meant the whole feature throwing immediately for a real, non-trivial fraction of users — a product-integrity issue, not a cosmetic one, so this was fixed at the root rather than left as a known issue or worked around by downgrading to an equally-affected older version.

**Fix**: a small, spec-accurate polyfill (`if (!this.has(key)) this.set(key, callback(key)); return this.get(key);` for the computed variant, same shape for the plain one), installed in two places because the worker runs in a separate JS realm with its own `Map.prototype` that a main-thread patch can't reach:

- `lib/scanning/map-upsert-polyfill.ts` — called from `load-pdf-file.ts` before any pdfjs API use, patches the main thread.
- `public/pdf-worker-shim.mjs` — a new committed static file. `GlobalWorkerOptions.workerSrc` now points here instead of at pdfjs's own worker file directly; the shim installs the same polyfill inside the worker's own realm, then `import()`s the real worker.

Both are one-line-documented, spec-clear, and narrowly scoped to the exact two methods pdfjs-dist actually calls (confirmed via the real call sites in its own bundled source, not guessed from the proposal text alone). Reproduced the failure, then reproduced the fix working, in a real browser both times (see "How this was tested") — this is a verified fix, not a plausible-looking one.

### 2. `useWasm: false` (JBIG2/OpenJPEG codec wasm not wired up) — a deliberate, narrower scope boundary

`getDocument()` is called with `useWasm: false`. Without it, a PDF page containing a JBIG2- or JPEG2000-compressed image would throw (`BinaryDataFactory not initialized`) the moment pdfjs tried to fetch the wasm codec for it, since this task doesn't also copy pdfjs's `wasm/` asset directory or wire a `wasmUrl` — and JBIG2 in particular is a common default for "black & white scan to PDF" on real scanner/MFP hardware, exactly the kind of file this loader exists to accept, so this isn't a contrived edge case. `useWasm: false` forces pdfjs's documented pure-JS decode fallback for those codecs instead (shipped in the same package specifically for this purpose) — correct output, just without native-speed decode, which doesn't matter at batch-import scale. Flagging the boundary explicitly: a PDF using these codecs works correctly today; it just doesn't get the wasm speed path. Wiring that up (copying `wasm/`, setting `wasmUrl`) is a bounded follow-up if it's ever shown to matter, not something quietly half-built here.

### 3. A benign, understood build-time console warning — not a functional issue

`npm run build` prints `Warning: Please use the \`legacy\` build in Node.js environments.`during static-page generation. Traced to its exact source in pdfjs-dist's own code: a plain`warn()`call, gated only on`isNodeJS`, with no other behavior attached to that check — it fires because Next.js's build-time module-graph analysis evaluates `load-pdf-file.ts`'s top-level `import` in Node (this app's static pages get prerendered), not because anything pdfjs-dist actually *does* differently. Every actual call (`getDocument`, `page.render`) only ever happens client-side, inside a `'use client'`component, where this branch never runs.`npm run build` still succeeds; this is a log line, not an error. Flagged so a future reader isn't alarmed by it and doesn't waste time re-investigating something already run to ground.

### 4. Pre-existing gap closed in passing: `tests/detection-harness/.generated/` had no `.gitignore` entry

Unrelated to this task's own feature, but directly adjacent: while adding a second generated-and-must-never-be-committed directory in the same area (this task's `.generated/vendor/pdfjs/`), found that `.generated/` itself (opencv.js + the esbuild bundle, since M1-010) was never actually covered by `.gitignore` — only by `eslint.config.mjs`'s ignore list. It's stayed out of every commit so far purely because this session's own git workflow adds files by name rather than `git add -A`, not because anything durably prevented it. Added a proper `.gitignore` entry for it alongside the new one this task needs, closing the gap rather than leaving it as a second, still-unprotected generated directory.

## What was built

- **`lib/scanning/read-sheet-from-image.ts`'s `detectAndReadSheet`** and **`exam-scan-mode.ts`'s `applyReadResult`** (both extracted as this task's own prerequisite, before the batch feature itself): the exact functions both live capture and batch import call — "the same review-queue/scoring path as live scans" (this task's own done-when wording) means literally the same function, verified by the extraction being fully behavior-preserving against the pre-existing live-capture test suite (31/31 green before any new code was added) and by 8 new dedicated unit tests for `applyReadResult` in isolation.
- **`lib/scanning/load-image-file.ts`** (new): loads a batch-imported image `File` to `ImageData`, downscaling to a 1920px cap — deliberately not M2-003's `image-loading.ts` (1600px, tuned for that task's different contour/HoughCircles detection algorithm); this cap instead matches the resolution live capture's camera feed actually requests (`camera.ts`'s `ideal: 1920x1080`), keeping batch-imported images inside the resolution range the read pipeline is actually proven at, per M2-004's own dewarpedDestRect precision lesson.
- **`lib/scanning/load-pdf-file.ts`** (new): renders a PDF's pages to `ImageData` one at a time via `pdfjs-dist` (pinned exact `6.3.289`, `dependencies` not `devDependencies` since its main library is bundled directly, unlike `@techstark/opencv-js`), exposing `{ numPages, loadPage(n) }` so a caller can show real "page N of M" progress and never holds every page's full-resolution pixels in memory at once. Its worker/CMap/standard-font assets are copied into `public/vendor/pdfjs/` on `predev`/`prebuild` (new `scripts/copy-pdfjs-assets.mjs`) — same "copy into `public/`, load by URL, don't make a bundler process it" approach `opencv-loader.ts` established, for the same reason (these are pre-built vendor assets meant to be fetched as-is).
- **`lib/scanning/map-upsert-polyfill.ts`** and **`public/pdf-worker-shim.mjs`** (new): the compatibility fix from Flag 1.
- **`app/(app)/exams/new/batch-import.ts`** (new): the batch queue's pure decision logic — `classifyFile` (image/PDF/unsupported), `startBatch`/`advanceBatch` (the `processing`→`done` state machine, tracking a `succeeded` count directly rather than deriving it from `items.length - failures.length`, which would double-count a pre-expansion rejection — see the dedicated regression test for exactly this), `keyAttemptRejection` (detects a rejected capture-key attempt from before/after `Mode` alone), and `buildBatchQueue` (expands picked files into a flat, page-level queue up front — a multi-page PDF contributes one item per page — with a bad file becoming an immediate, isolated failure rather than aborting the whole batch).
- **`app/(app)/exams/new/exam-scan-flow.tsx`**: a file input + "Import files" button, wired to a `useEffect` keyed on `[batch, mode, geometry]` that drives one queue item at a time through `loadOpenCv`/`loadImageFile`-or-`loadPage`/`detectAndReadSheet`/`applyReadResult` — the exact same call live capture makes, just fed a batch item's pixels instead of a camera frame. The effect's own guard clause (`if (mode.pendingDuplicate) return`) is the entire pause mechanism: no separate pause/resume plumbing was needed, since `applyReadResult` already returns `pendingDuplicate` set instead of saving a colliding roll number, and the effect naturally stops advancing the moment that happens and resumes once the teacher's pre-existing confirm/cancel handlers clear it. While a batch runs, the live-capture effect stands down (`batchActive` guard) and the Review Queue button is disabled — the one piece of state-mutation surface that could otherwise race the batch loop's own read-then-`setMode` step, since everything else that can touch `mode` during a batch either is the batch loop itself or is the duplicate-dialog's own handlers, which the loop already treats as its synchronization point. Progress ("Processing sheet N of M" + the current item's label) and an end-of-batch summary (succeeded count + every failure's label and reason, dismissible) are both shown as overlays; a first batch item can itself become the answer key, exercised by a dedicated test, since `applyReadResult`'s `capture-key` branch needed no special-casing to reach through the batch loop.
