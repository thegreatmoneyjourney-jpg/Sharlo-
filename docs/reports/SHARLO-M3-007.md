**Status: done.** Builds `FR-ROSTER-01`/`FR-ROSTER-02` on top of the `M3-006` envelope primitives, and closes the forward reference both `lib/scanning/roll-number.ts` (`M1-009`) and `lib/scanning/review-queue.ts` (`M2-006`) explicitly left open for "once a roster/class-list data model exists."

## Flags

1. **An apparent tension between three SRS/TASKS passages — resolved by reading them together, not escalated.** `docs/SRS.md`'s Free/Pro/School feature-gating table describes `FR-ROSTER-01`'s roster as "the ad-hoc, per-exam roster — not the same as Class Management below," which read in isolation suggests a different underlying record from the future Class Management feature (`M8`, not yet authorized). But `FR-ATTEND-02` is explicit in the opposite direction — "this roster is the _same_ underlying record `FR-ROSTER-01`'s per-exam CSV upload populates... not two parallel student lists" — and `docs/TASKS.md`'s own `M8-001` row confirms it a third time ("the same underlying record... not a parallel list"). Read together, there's no real contradiction: the feature-gating table is about which _feature surface_ a tier gets (Free: CSV-upload-per-class only; Pro/School: also `M8`'s fuller Class Management UI), not about the data model. This task built the roster as a class-keyed persistent record from the start (one envelope per class, reusable across exams), matching `FR-ATTEND-02`'s literal instruction — `M8` will build a management UI on these same envelopes later, never migrate off them. This is recorded here as a Key Decision, not in `ARCHITECTURE.md` §15's resolution log — that log is for architecture questions escalated to and resolved by the founder, and this one wasn't; it was resolvable from the existing docs alone.
2. **A genuine, necessary prerequisite gap surfaced and closed: there was no session-wide master-key mechanism anywhere in the app before this task.** Every encryption/decryption operation through `M3-006` unwrapped the master key transiently inside one handler (`settings-client.tsx`'s passphrase-change/Recovery-Key-rotation flows) and let it go out of scope immediately after — fine for an action the teacher takes once, but unworkable for a feature that needs to encrypt/decrypt repeatedly across a session (roster upload here; exam-results persistence next, `M3-008`) without re-prompting for the passphrase before every single operation. Built as a small, reusable primitive (`lib/crypto/master-key-session.ts` + `app/(app)/use-master-key.ts`/`require-master-key.tsx`) rather than ad-hoc-ing it into the roster UI alone, since `M3-008` will need the identical thing immediately next. Not a stop condition — this was a normal, well-constrained engineering judgment call (in-memory-only, mirrors `M3-006`'s own Drive-access-token caching precedent), not an architectural ambiguity requiring founder input.
3. **A real, pre-existing cross-file test race (unrelated to rostering) was found and fixed while verifying this task's own `npm run ci` run, not glossed over.** `apps/api/test/recovery-key-reminders.test.ts` (`M3-004`) asserted on `sendMock`'s raw call count and `runRecoveryKeyReminderSweep`'s raw result totals — but that sweep genuinely sweeps the _entire_ `users` table by design (a real cross-tenant scheduled job), and `apps/api/test/encryption-routes.test.ts` (also `M3-004`) has two tests that briefly backdate a different, unrelated user's `recovery_key_issued_at` via direct SQL to exercise the reminder-status endpoint, cleaning up immediately after but still leaving a real, narrow window a concurrently-scheduled sweep call can observe. This reproduced as a real failure once during this task's own CI verification (not a flake dismissed without investigation) — root-caused, confirmed to pass reliably in isolation (ruling out stale sandbox data as the cause), and fixed by scoping every assertion in `recovery-key-reminders.test.ts` to the specific emails/reminder-kind _that test itself_ seeded, never to the sweep's global totals. See "How it was tested" below for the full before/after. Flagged here per this project's standing discipline of never presenting a fix as unrelated noise when it was a real bug this task's own verification pass surfaced.
4. **Not verified against real student-filled sheets, a real roster CSV from a real school, or a real device** — the same category of gap `M1-011` (real-device scanning), `M3-001` (real iOS Safari), and `M3-006` (real Google Drive account) already carry for this project, not a new one. Every test here uses synthetic fixtures and mocked network/storage boundaries.

## What was built

**`apps/web/lib/roster/` (new directory):**

- `parse-csv.ts` — a hand-rolled RFC4180-ish tokenizer (quoted fields, embedded commas/newlines, escaped quotes, CRLF/LF, a leading UTF-8 BOM stripped, blank lines skipped anywhere). Deliberately generic text → rows, no roster-specific interpretation.
- `roster.ts` — the roster data model and matching logic: `RosterEntry`/`Roster` types; `parseRosterCsv` (header auto-detection via "is the first cell all-digits," per-row validation that skips and reports a bad row — non-numeric roll number, missing name, a duplicate — rather than discarding the whole upload or silently keeping an unmatchable entry, and surfaces the skipped header row to the UI instead of silently guessing); `normalizeRollNumber` (strips leading zeros so a scanned sheet's fixed-width zero-padded roll number and a freely-typed CSV cell agree on identity); `buildRosterLookup`; `resolveRollNumberAgainstRoster` (the integration point — wraps `roll-number.ts`'s existing, already-tested `matchRollNumber` rather than reimplementing membership, and is the single place that decides "no roster selected" still means exactly what it always meant: accept the read value as-is, no name attached).
- `roster-store.ts` — `saveRoster`/`listRosters`/`loadRoster`, a thin wrapper over `M3-006`'s `encryptEnvelope`/`decryptEnvelope` and the `EnvelopeStore` interface (dependency-injected, not resolved internally, matching this codebase's existing test-seam pattern).

**`apps/web/lib/crypto/master-key-session.ts` + `apps/web/app/(app)/{use-master-key.ts,require-master-key.tsx,unlock-master-key-prompt.tsx}` (new):** the session-wide master-key cache and its React hook/wrapper component — see Flag 2.

**`apps/web/app/(app)/exams/new/` (modified/new):**

- `roster-picker.tsx` (new) — the inline class-list UI: pick an existing class, upload a new one, or replace an existing class's list in place (reusing its `recordId`), with a CSV preview showing entry count, any skipped header row, and any per-row errors.
- `new-exam-client.tsx` — a collapsed "Add a class list (optional)" toggle; `RequireMasterKey` + `RosterPicker` only mount once the teacher opts in, so a teacher who never touches it sees zero behavior change (no passphrase prompt, no extra network call) from before this task.
- `exam-scan-mode.ts` — `StudentResult` gains `name: string | null`, populated by `applyReadResult` from the roster match already resolved upstream (never recomputed); the roll-number review-queue item gains `reason`/`readValue`.
- `exam-scan-flow.tsx` — threads the resolved `roster: ReadonlyMap<string,string> | null` prop into both the live-capture (`useSheetReader`) and batch-import (`detectAndReadSheet`) call sites; `resolveRollNumberItem` (manual correction) also does a roster lookup for the name; the live status card shows the matched name when available.
- `review-queue-panel.tsx` — shows a reason-specific message ("no matching student on the roster" vs "couldn't be read") and pre-fills the correction input with whatever value was actually read, so a teacher confirming/correcting an unmatched-but-read roll number isn't retyping a number the scanner already got right.

**`apps/web/lib/scanning/` (modified, minimal, by design):**

- `review-queue.ts`'s `buildReviewItemSpecs` takes a plain `{reason: 'unread'|'unmatched'} | null` third parameter instead of a raw `RollNumberReadResult` — it still never imports or knows about `lib/roster/`, preserving the layering `roll-number.ts`'s own doc comment anticipated.
- `read-sheet-from-image.ts`'s `readSheetFromCorners`/`detectAndReadSheet` take an optional `rosterLookup` parameter (default `null`, preserving exact prior behavior) and resolve the match once, exposing it as `SheetReadOutcome.rollNumberMatch` for every downstream consumer.
- `tests/detection-harness/browser-entry.ts`'s `runReviewCropCase` updated for the new `buildReviewItemSpecs` signature (no roster concept in that harness — "unreadable" is the only case that still triggers a crop, matching the exact pre-existing behavior).

## Key decisions

- **Roster envelope granularity: one per class, not one per exam** — see Flag 1.
- **Roll-number matching normalizes by stripping leading zeros, comparing numeric identity rather than exact string equality** — a template's roll-number bubble grid is a fixed-width, zero-padded encoding whose width is a property of the template, not the roster; different exams for the same class could even use different templates.
- **The master-key session cache is in-memory only, module-level state** — never `localStorage`/IndexedDB/a cookie, the same tradeoff `M3-006`'s Drive-access-token cache already made. Unlike that token, a master key can't be silently "refreshed" without the passphrase, so losing the cache (reload, or an explicit `lock()`) means asking again, not a background retry.
- **`RequireMasterKey` only mounts, and `useMasterKey` only fetches `/account/encryption-params`, once the teacher opts into rostering** — not unconditionally on every exam-setup page load. Keeping the no-roster path's network/UX footprint at exactly zero was treated as a hard constraint, not a nice-to-have, given how much of this app's existing flow (exam creation, scanning) has no reason to touch the master key at all.
- **`review-queue.ts` stays fully agnostic of `lib/roster/`** — the roster-match-to-review-reason translation happens in `read-sheet-from-image.ts` (already the M2 integration layer that knows about templates/geometry), not in the lower-level, previously-agnostic `roll-number.ts`/`review-queue.ts` modules. Kept the dependency direction clean rather than letting a product-domain concept leak into what had been reusable, representation-agnostic primitives.
- **No delete-a-class affordance** — `roster-store.ts` supports create/list/load/replace-in-place but not delete. Not required by `FR-ROSTER-01`/`02`'s literal scope, and a reasonable small follow-up once it's a real pain point rather than built speculatively now.
