## 🚩 Flags — read this section first

Nothing blocked. Three things worth flagging explicitly:

1. **The specific marker scheme (`DICT_4X4_50`, fixed IDs 0-3 for the four corners) is a placeholder pending M2-001, not a confirmed product decision.** M1-003 can't detect corner markers without committing to *some* concrete dictionary and ID assignment, but the real answer — what marker set Sharlo's stock templates actually use, and whether all templates share one fixed ID assignment or vary per template — is M2-001's ("Sharlo stock template library") job to define. `DICT_4X4_50` was chosen because it's a small, robust, commonly-used ArUco dictionary well suited to a printed-paper context, and IDs 0-3 mapped to named corners (rather than inferring corner identity from position) is a deliberate, defensible default — see "Key decisions" below — but whoever picks up M2-001 needs to explicitly confirm or revise this, not assume it's load-bearing. `corner-markers.ts` has a doc comment pointing back to this report.

2. **Methodology correction, worth remembering for any future OpenCV.js API question on this repo:** the first attempt to check whether ArUco detection was even available in `@techstark/opencv-js` used a plain text search (grep, then a Python string search) of the bundled `opencv.js` file for ArUco-related symbols. It found nothing, and the session nearly concluded ArUco wasn't available — which would have meant hand-rolling contour/square-based corner detection instead, redoing work OpenCV already does robustly. That conclusion was wrong: this is a WASM+embind build, and embind's actual bindings live inside the compiled WASM binary (base64-embedded in the JS as a data URI), not as readable JS text, so no text search of the bundle can ever find them — a `grep` miss proves nothing about a WASM-embind build's real API surface. The correct method, used from that point on: verify via real in-browser runtime introspection (`typeof cv.foo`, actually constructing classes and reading the arguments-count errors when a guessed signature is wrong). This is how ArUco's actual (flat-prefixed, e.g. `aruco_ArucoDetector`, not a `cv.aruco.*` namespace) API surface was found and confirmed. Any future "does OpenCV.js support X" question on this repo should start with runtime introspection, not grep.

3. **M1-003's "done when" criteria are only partially verified, and the gap is real, not just a formality.** The two criteria in `TASKS.md` are "≥10fps sustained on reference device (NFR-PERF-03)" and "detection success rate measured against a sample-sheet test set." What's actually been verified — precisely, so the gap is clear:
   - **Correctness and integration**, end to end, with the real production code (not a reimplementation): all 4 markers detected and correctly identified by name, centroids accurate to ~0.5px of known ground truth, against **one** synthetically generated sheet image, in a real Chromium page (not jsdom/mocked).
   - **Throughput** on that same one image, in that same sandboxed Chromium instance, with no real camera or device involved: 35.68ms average per `detect()` call over 20 runs (~28fps implied) — comfortably above the 10fps floor, but this is this sandbox's software rendering performance, not a measurement on any "reference device" as NFR-PERF-03 literally asks for. Same category of limitation as M1-002's flagged gap (no camera hardware available in this sandbox) — noted there as accepted practice for this project rather than a blocker.
   - **What's genuinely not measured**: NFR-ACC-01's actual target — "≥98% success... under adequate lighting and ≤15° sheet tilt" — needs a varied sample-sheet set (multiple images, varied tilt angles, varied lighting/contrast, realistic print/camera noise) to mean anything as a success *rate*. Twenty repeated detections of one clean, untilted, ideally-lit synthetic image is a correctness/perf proof-of-function, not a rate measurement across conditions. This isn't an oversight: `TASKS.md` already assigns the proper fix for this gap to **M1-010** ("Detection engine unit test harness... reusable fixture-based test harness... for M1-003 through M1-009"), i.e. the milestone plan already anticipates that M1-003 alone can't fully close this criterion and defers the real fixture-set infrastructure to a dedicated later task applied retroactively. Building an ad hoc version of that harness now, inside this task, would duplicate M1-010's work and wasn't attempted. Flagging this plainly now rather than letting "detection success rate measured against a sample-sheet test set" read as fully satisfied when it's actually a single favorable data point.

None of the above blocks M1-003 from being considered functionally done — the algorithm is implemented correctly, integrates correctly with the real camera/OpenCV pipeline, and performs well on the one case tested. It blocks treating the milestone's stated done-when criteria as *rigorously* satisfied, which is a different and narrower claim.

## What was built

- **`apps/web/lib/scanning/corner-markers.ts`** — `CornerMarkerDetector` wraps `cv.aruco_ArucoDetector` (dictionary `DICT_4X4_50`, `CORNER_REFINE_SUBPIX` for sub-pixel corner accuracy) behind a typed `ArucoCv` surface that extends `opencv-loader.ts`'s existing `OpenCvRuntime`. `detect(frame)` returns a discriminated `CornerDetectionResult`: `{ complete: true, corners: {...all 4...} }` only once every one of `topLeft`/`topRight`/`bottomRight`/`bottomLeft` is found by its assigned marker ID, otherwise `{ complete: false, found: {...whatever subset was found...} }` — there is no code path that fabricates or interpolates a missing corner's position. Every intermediate `cv.Mat`/`MatVector` (corners, ids, rejected, and each per-marker corner Mat) is freed in a `finally` block regardless of outcome.
- **`apps/web/app/(app)/scan/use-corner-detection.ts`** — drives the detector against the live `<video>` element: an offscreen canvas captures each frame (`drawImage` → `getImageData` → `matFromImageData`), throttled via `requestAnimationFrame` to a 12fps target (10fps floor + headroom for frame-timing jitter). Fully inert when `active` is false — no frames captured, no CPU spent, no OpenCV calls made — which matters since this runs continuously once live. Reports the latest detection result plus a trailing ~1-second measured fps.
- **`apps/web/app/(app)/scan/scan-client.tsx`** (updated) — wires the hook in behind the existing OpenCV+camera "ready" gate (`useCornerDetection(videoRef, ready)`), and adds a canvas overlay sized to the video's intrinsic resolution: a green ring per corner once all 4 are found, amber for whatever subset is found so far, plus a small fps readout once measured. Purely a visual proof this task's detection loop is actually running against live frames — *acting* on a stable detection (stability gate, perspective transform, auto-capture) is M1-004 onward and is explicitly out of scope here.
- **Tests**: `corner-markers.test.ts` — 5 new unit tests against a hand-built fake `ArucoCv` (complete detection with correct centroids, incomplete detection that never guesses the missing corner(s), unrecognized marker IDs ignored rather than mis-assigned, empty-detection case, and a cleanup test asserting the exact expected `delete()` call count). `scan-client.test.tsx` — updated with a `use-corner-detection` mock (the real hook needs actual WASM execution and can't run in jsdom) and new tests: detection only activates once both OpenCV and the camera are ready, fps readout shown once measured / absent before that.

## Key decisions

### 1. ArUco over hand-rolled contour/square detection

Once confirmed available (see Flag 2 above), ArUco was the clear choice over writing custom contour-finding/quadrilateral-scoring logic: it's purpose-built for exactly this problem (detect several ID-encoded markers robustly under real-world camera conditions), already present in the pinned `@techstark/opencv-js` build at no extra bundle cost, and sub-pixel corner refinement (`CORNER_REFINE_SUBPIX`) is a solved, tested part of the library rather than something to get right from scratch.

### 2. Corner identity comes from the marker's encoded ID, not its position in the frame

`CORNER_MARKER_IDS` maps specific ArUco IDs directly to `topLeft`/`topRight`/`bottomRight`/`bottomLeft`, and `detect()` names each found marker by looking up its decoded ID — it never infers "top-left" from "whichever marker has the smallest x+y" or similar positional heuristics. This is deliberately robust to the sheet being rotated in frame (a teacher is not going to hold up a bubble sheet perfectly axis-aligned to the camera): whichever physical corner carries the marker encoded as ID 0 is `topLeft` regardless of where that lands in the captured image. It also means the centroid computation (a plain average of a marker's 4 corner points) is correct regardless of marker rotation, since it doesn't depend on corner winding order.

### 3. The "never guess" result shape is enforced at this layer already, not deferred entirely to bubble-reading

`CornerDetectionResult` is a discriminated union specifically so `complete: true` is only reachable with all 4 corners actually present — there's no default/fallback corner object anywhere in the type or the implementation. NFR-ACC-03 ("never auto-guess... err toward flagging for review") is usually discussed in the context of ambiguous bubble marks (M1-006), but the same discipline applies here: a caller of this detector structurally cannot mistake a partial detection for a complete one.

### 4. Detection throttled to 12fps and fully paused when inactive

10fps is the NFR-PERF-03 floor; targeting 12 leaves headroom so ordinary frame-to-frame timing jitter doesn't dip the *sustained* rate below it. Gating the entire effect (including the `loadOpenCv()` call chain and the `requestAnimationFrame` loop) behind `active` means the cost of this feature is zero whenever the camera isn't live yet — relevant on mobile, where the OpenCV+camera loading phase can take a couple of seconds and shouldn't be spending CPU/battery on detection during that time.

## How this was tested

- **`npm run ci`** (format, lint, typecheck, test) — green at repo root. 35/35 tests passing in the `web` workspace (up from 30 before this task: 5 new `corner-markers.test.ts` tests; `scan-client.test.tsx`'s existing tests continue passing against the new mock).
- **Real browser, real bundled code** — the actual `apps/web/lib/scanning/corner-markers.ts`, bundled with `esbuild` (not a reimplementation or a mock of the detection logic), loaded in a real Chromium page (Playwright, this environment's pre-installed browser) alongside the real `opencv.js`. A synthetic 1000×1300 "sheet" canvas was generated with 4 real ArUco markers (drawn via OpenCV's own `generateImageMarker`, not hand-drawn bitmaps) at known positions, then run through the exact same `canvas → getImageData → matFromImageData → detect()` chain `use-corner-detection.ts` uses in production, 20 times:
  - All 4 corners detected and correctly named every time.
  - Centroid positions accurate to ~0.5px of known ground truth (e.g. `topLeft` detected at `{x: 79.5, y: 79.5}` vs. an expected `{x: 80, y: 80}`).
  - 35.68ms average per `detect()` call (range ~31.5-64.2ms across 20 runs, the one outlier being the first/cold call), implying ~28fps — well above the 10fps floor in this environment.
- **Not done, explicitly (see Flag 3 for why this matters and isn't silently skipped)**: a varied sample-sheet test set (multiple images, tilt angles, lighting/contrast conditions) needed to actually measure a success *rate* against NFR-ACC-01's 98% target; any measurement on physical mobile hardware (no camera/device available in this sandbox, same limitation class as M1-002).
