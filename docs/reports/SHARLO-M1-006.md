## 🚩 Flags — read this section first

Nothing blocked. This task carries CLAUDE.md's explicit high-severity bar ("Never auto-guess an ambiguous bubble mark... a regression here is a product-integrity bug"), so this section is longer and more detailed than prior ones on purpose — this is the one place in M1 where "close enough" isn't an acceptable standard, and the flags below are written so a future reader doesn't have to re-derive what was and wasn't actually established.

1. **A real algorithmic gap was found and fixed via this task's own real-browser verification — read this in full, not just as a "bug fixed along the way" note.** The first implementation of `sampleBubbleFillRatio` used a binary per-pixel darkness threshold (a pixel counts as "dark" or not, then the fraction of dark pixels is the fill ratio). Verified against **actually-rendered canvas pixels** (not hand-constructed `ImageData` arrays — real anti-aliasing, real alpha blending), a uniformly faint mark (`rgba(0,0,0,0.3)` on white, simulating light, even pencil pressure across the whole bubble) came back with fill ratio **0**, classified **confident-empty**. The reason: every pixel in a uniform region lands on the same side of a fixed cutoff, so "fraction dark" collapses to 0 or 1 regardless of how genuinely gray the region is — a second, hidden binary decision baked into what was supposed to be a continuous confidence measure. A real faint mark could have silently read as no-answer instead of being flagged for review. **Fixed** by switching to a continuous mean-luminance approach (`fillRatio = 1 - meanLuminance/255`), which correctly returns an intermediate ratio for a uniform faint fill while still handling partial-coverage marks (a small dark scribble on an otherwise-white bubble) the same way it always did. Re-verified clean after the fix — see "How this was tested" for the specific before/after numbers.
2. **A second bug, in the verification script itself, is worth naming so it doesn't read as silently swept aside.** The first real-browser run of the "one option filled, rest blank" scenario produced `{ outcome: 'blank' }` instead of the expected `{ outcome: 'answered', optionIndex: 2 }` — investigated and traced to the _test script_, not the product: `ctx.fillStyle` was left over from an earlier test scenario (accidentally `'white'`) when the "filled" bubble's `ctx.fill()` call ran, so the "filled" bubble was actually invisibly filled with white and read _emptier_ than the genuinely-blank outlined bubbles next to it. Fixed by setting `ctx.fillStyle` explicitly at every fill call rather than relying on it carrying over correctly between test blocks. Documented because a wrong test result that turns out to be a test bug, not a product bug, still needs to be run down and explained, not just "fixed and moved on" — this report says so explicitly rather than presenting the final clean numbers as if they were the first ones observed.
3. **One borderline case was found and deliberately left as an open, real-world-tuning question rather than resolved here.** A bubble filled solid, then roughly half "erased" (white drawn back over the top half) came back with fill ratio ≈0.49, just above the 0.45 `filledAtOrAbove` threshold — classified `confident-filled`. This is a defensible call (half the bubble genuinely is still solid dark) but is exactly the kind of case NFR-ACC-03/04's tuning tradeoff exists to resolve with real data, not a synthetic single example. Not changed without real samples to justify a specific new number.
4. **Default thresholds (`emptyAtOrBelow: 0.15`, `filledAtOrAbove: 0.45`) are placeholders pending real-world tuning** — explicitly anticipated by ARCHITECTURE.md §4 step 5 ("the single biggest lever on the NFR-ACC-03 vs. NFR-ACC-04 tradeoff... should be tunable constants") and SRS §6.2 (NFR-ACC-02/03's numeric targets are themselves flagged as "engineering starting targets... needing empirical validation against real printed/scanned sample sheets," not yet validated). Same placeholder category as every prior M1 task's flagged constant — not a new kind of gap, just this task's instance of it.
5. **Scope boundary, stated plainly so it isn't mistaken for an oversight:** this task does not read a whole answer sheet or know about a bubble grid's layout. It samples and classifies _caller-supplied_ bubble regions (a center + radius) and _caller-supplied_ question groupings (arrays of fill ratios). `TASKS.md`'s own description — "sample **each** bubble region" — presupposes a caller that already knows where the bubbles are; that caller is a real template reader, which needs M2-001/M2-002's actual template geometry to exist first. Consequently, **this task's code is not wired into `scan-client.tsx`**, unlike M1-003 through M1-005, which each added a small live-camera visual proof. Wiring in a placeholder bubble grid now would mean either inventing fake geometry that a future reader could mistake for a real product decision, or overlaying a meaningless grid on real camera frames — neither is an improvement over the thorough unit + real-browser-pixel testing this task already has. If a future session reaches for a "why isn't this in the live UI yet" question, this is the answer.

## What was built

- **`apps/web/lib/scanning/bubble-fill.ts`**:
  - `sampleBubbleFillRatio(imageData, region)` — `1 - meanNormalizedLuminance` over a bubble's circular pixel region in an `ImageData`. No OpenCV dependency — plain pixel-region statistics, which is deliberate (see "Key decisions").
  - `classifyBubbleFill(fillRatio, thresholds?)` — closed/closed threshold boundaries with an open ambiguous interior (`≤ emptyAtOrBelow` → confident-empty, `≥ filledAtOrAbove` → confident-filled, otherwise ambiguous), so every real number maps to exactly one classification.
  - `classifyQuestion(fillRatios, thresholds?)` — the actual trust-guarantee enforcement function. Returns `{ outcome: 'answered', optionIndex }`, `{ outcome: 'blank' }` (every option confidently empty — a common, legitimate, _not flagged_ outcome, distinct from genuine ambiguity), or `{ outcome: 'flagged' }` (any ambiguous option, or multiple confidently-filled options). There is no code path that returns `'answered'` from anything other than exactly-one-confident-filled-and-the-rest-confident-empty.
- **Tests**: `bubble-fill.test.ts` — 21 tests: `sampleBubbleFillRatio` against hand-built `ImageData` (fully dark, fully white, split regions, out-of-bounds regions, and the uniform-faint-fill regression case described in Flag 1); `classifyBubbleFill`'s boundary behavior; `classifyQuestion`'s normal cases; and a dedicated, prominently-labeled **"never guesses — deliberately ambiguous inputs always flag"** parameterized suite covering 9 distinct ambiguous combinations (multiple marks, all-filled, a lone ambiguous bubble alongside otherwise-empty options, a confidently-filled option alongside a merely-ambiguous one, values one step inside the ambiguous zone on either boundary, etc.) — this suite is `TASKS.md`'s own done-when criterion for this task, implemented as an actual, always-run regression test, not just described in a comment.

## Key decisions

### 1. Pixel math on `ImageData`, not OpenCV

Computing mean darkness inside a circular region doesn't need OpenCV's machinery — it's arithmetic over a typed array. Keeping this module OpenCV-free means the single most safety-critical logic in the whole scanning pipeline is directly unit-testable in a plain Node/jsdom environment, and runs in CI on every push. Every prior M1 task's core logic (M1-003 through M1-005) needed real-browser WASM execution to verify correctly — this is the first M1 task where the core trust-guarantee logic itself is a CI-enforced regression suite, not a sandbox-only check. That's a meaningfully stronger guarantee for the one piece of this codebase CLAUDE.md singles out as high-severity if it regresses.

### 2. Continuous mean luminance over a binary per-pixel threshold (the bug fix, elevated to a documented design decision)

Beyond fixing Flag 1's bug, this is simply the more capable model: it correctly represents both failure modes NFR-ACC-02's acceptance criteria name — "partial fill" (a small dark scribble covering part of an otherwise-white bubble; correctly produces an intermediate ratio because the covered fraction proportionally lowers the mean) and, now, a uniformly faint mark (correctly intermediate because the whole region's actual gray level is preserved, not binarized away). A binary threshold could only ever detect one of these two ambiguity shapes.

### 3. `blank` is not `flagged`

A question every option of which is confidently empty is not ambiguous — it's a clear signal the student didn't answer, which is common (especially near the end of a timed exam) and shouldn't inflate the Review Queue. Conflating "confidently nothing marked" with "genuinely unclear what was marked" would work directly against NFR-ACC-04's flag-rate target without any accuracy benefit. `classifyQuestion`'s three-way `QuestionResult` keeps these distinct on purpose.

### 4. No dedicated erasure-smudge detector

An eraser smudge and a genuine partial fill produce the same signal this algorithm can see — an intermediate, non-uniform darkness — so the same threshold mechanism that catches partial fills catches smudges too, without needing separate logic to tell them apart. Flag 3's borderline case shows this isn't perfect, but building a dedicated smudge classifier without real erased-sheet samples to validate against would be speculative engineering against a problem not yet empirically characterized.

## Deviations from the task description

The scope boundary in Flag 5 (no grid-template invention, no `scan-client.tsx` wiring) is the one thing worth naming as a deviation from this milestone's established per-task pattern (M1-003 through M1-005 each added live-UI wiring) — reasoned through above, not an oversight.

## How this was tested

- **`npm run ci`** (format, lint, typecheck, test) — green at repo root. 81/81 tests passing in the `web` workspace (up from 60).
- **Real browser, real rendered pixels** — Playwright, actual canvas rendering (not hand-constructed pixel arrays), against the real `sampleBubbleFillRatio`/`classifyBubbleFill`/`classifyQuestion` (bundled with `esbuild`, not reimplemented):
  - **Before the fix**: a uniformly `rgba(0,0,0,0.3)`-filled bubble → ratio `0` → `confident-empty` (wrong — this is what Flag 1 describes). A rendered "one filled, three blank" question → `{ outcome: 'blank' }` (wrong — this is Flag 2's test-script bug).
  - **After both fixes**: fully filled bubble → ratio `0.959` → `confident-filled`. Blank outlined bubble → ratio `0.130` → `confident-empty`. The same light partial mark → ratio `0.290` → `ambiguous` (correct this time). A half-erased mark → ratio `0.488` → `confident-filled` (Flag 3's open borderline case). A real rendered 4-option question with exactly one filled bubble → `{ outcome: 'answered', optionIndex: 2 }`. A real rendered 4-option question with two filled bubbles → `{ outcome: 'flagged' }` — the core guarantee, holding against real pixels, not just a synthetic array.
- **Not done, explicitly**: statistical validation of NFR-ACC-02's ≥99.5% agreement-with-ground-truth target or NFR-ACC-03's ≤0.5% silent-misread target — both require a large, varied, real (or realistically-representative) sample set, which is M1-010's job (and ultimately real-world beta data), not something a handful of synthetic canvas-rendered bubbles can establish. What _is_ established here: the classification logic has no code path that guesses, verified both by exhaustive-style parameterized unit tests and by real rendered pixels — that's a correctness guarantee, not yet a statistical accuracy one.
