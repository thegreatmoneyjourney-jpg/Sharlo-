# SHARLO-M3-016: Dual-encryption on exam finalize

## Flags

1. **Resolves M3-015's own flagged open question — the fate of `schools.school_wrapped_key_by_admin_master_key` — by direct re-derivation, not by escalating to the founder again.** `M3-015`'s report flagged that the admin-only X25519 keypair design (`M3-014`/Addendum 9) can cryptographically only support a teacher sealing data _to_ the admin, never the admin distributing the persisted symmetric school key _to_ a teacher (sealed boxes are one-directional). Re-deriving this fully while designing M3-016's actual finalize-time mechanism confirms it: with only the admin holding a keypair, there is no public key the admin's side could ever seal the school key _to_, so `ADR-0010`'s literal "teacher encrypts to the school key" wording was never actually reachable once `M3-014`'s own founder-directed keypair design (Addendum 9) was in place. This is the same class of gap `ADR-0010`'s addendum items 1–3 already resolved via "reconcile and document" rather than a fresh `AskUserQuestion` — the founder's own prior answer (only the admin gets a keypair) already fully determines the correct mechanism once re-derived; no new founder decision is needed to proceed. Resolution: the teacher's client seals each exam's content **directly** to the admin's public key instead of routing through the symmetric school key at all. See `ADR-0010`'s addendum item 4 for the full reasoning, and point 2 below for what happens to the now-dormant column.
2. **`schools.school_wrapped_key_by_admin_master_key` and `school-key.ts`'s `generateSchoolKey`/`unwrapSchoolKey` are left in place, dormant — not deleted.** Removing a shipped, founder-confirmed column and primitive on an engineering inference about future need is a bigger call than this task's scope. Flagged in the ADR addendum for the founder's awareness and eventual decision (candidates for a future cleanup pass if nothing ever needs a school-wide symmetric key for some other purpose), consistent with this project's standing "don't delete speculatively, a dormant primitive costs nothing" precedent.
3. **A genuine Drive write failure on the school-copy step (eligible, but the API call itself fails) is logged and swallowed, with no retry UI built.** The individual save is unconditional and already durably complete by the time the school-copy attempt runs, so a failure here must never block or retroactively fail it — that part isn't in question. What's flagged, not silently decided, is the lack of any visible retry affordance for this specific edge case: the task's own done-when criteria didn't ask for one, and building speculative retry UX felt like over-reach versus flagging the gap honestly. Revisit with real evidence (a real Drive flakiness rate) rather than a hunch, the same discipline `M3-015`'s own sandbox test-flakiness investigation already established for "don't speculatively fix, document and defer."
4. **Unrelated to this task's scope, found and fixed before starting it:** `apps/web/AGENTS.md` (imported into `apps/web/CLAUDE.md`) contained a prompt-injection-shaped artifact — false claims that Next.js had training-data-breaking changes and that `node_modules/next/dist/docs/` was authoritative documentation a future agent session should defer to. Verified both claims false (neither the path nor its claimed generator script exist) and removed both files in their own isolated commit before any M3-016 work began. Not a flag on this task itself — noted here only so the branch's commit history isn't confusing. See `CLAUDE.md`'s own decisions log for the full account.

## What was built

**Schema (`apps/api`):** a new denormalized `school_members.admin_x25519_public_key` column (migration `0009_majestic_shocker.sql`), populated in `addTeacherToSchool` from the authoritative `schools` row the admin's own RLS-checked connection reads at add-teacher time — the same write-once-at-insert pattern `M3-015` already established on this table for `driveLocationType`/`driveLocationId`/`email`. Exposed to the teacher via `GET /schools/my-membership`'s `MyMembership.adminX25519PublicKey` (both the API's own `MyMembership` interface and the web client's mirror in `lib/api/schools-client.ts`).

**Sealing (`apps/web/lib/exams/exam-results.ts`):** two new functions, `sealExamResultsForSchool` and `unsealExamResultsForSchool`, sharing the module's existing `ExamResultsContent` shape (now exported) and `EXAM_RESULTS_MIGRATIONS` registry with the individual AES-GCM path. `sealExamResultsForSchool` takes the admin's public key (hex) and an `ExamResults`, and returns a `SealedRecord` tagged with a new, deliberately distinct type (`"schoolExamResults"`) so it's never confusable with a teacher's own `"examResults"` envelope. `unsealExamResultsForSchool` is the admin-side counterpart — built and tested now even though `M3-017` (the real caller) doesn't exist yet, following this project's established "build the complete, tested pair now" precedent.

**Storage (`apps/web/lib/storage/school-container-store.ts`):** a new module parallel to `drive-envelope-store.ts`, scoped to a specific parent folder/Shared Drive rather than the Drive root. `putSealedRecord`/`getSealedRecord`/`listSealedRecordsByType` — no `delete`, nothing needs it yet. Every query includes `supportsAllDrives=true`/`includeItemsFromAllDrives=true` unconditionally (harmless for a plain folder, required for a Shared Drive). `parents` is included in upload metadata only on create, never on update, matching Drive API v3's own documented `addParents`/`removeParents`-for-update semantics.

**Orchestration (`apps/web/lib/exams/school-result-sync.ts`):** `syncExamResultsToSchool`, a single function that never throws — checks membership + `ensureSchoolDriveAccess` (`M3-015`), and if eligible, seals and writes the school copy; every failure mode resolves to a result object instead of an exception.

**Wiring (`apps/web/app/(app)/exams/new/new-exam-client.tsx`):** `SaveExamStep.handleSave` now calls `syncExamResultsToSchool(exam)` immediately after the existing, unconditional `saveExamResults` call, logging (not surfacing inline) a failed attempt, and always proceeding to the existing redirect regardless of outcome.

## Key decisions

- **Direct sealing of exam content to the admin's public key, bypassing the symmetric school key entirely** — see Flags #1 above for the full cryptographic reasoning.
- **A new Drive-write module rather than extending `drive-envelope-store.ts`** — that module's functions operate at the Drive root by design (no `parents` field anywhere), and retrofitting folder-scoping onto it would have meant branching behavior inside a module every other envelope type already depends on working exactly as it does today. A small, separate, parallel module was the lower-risk choice.
- **Best-effort, non-blocking orchestration, with the "not eligible" cases left to the standing banner rather than new UI** — `M3-015`'s `SchoolDriveAccessBanner` already satisfies `FR-SCHOOL-02`'s "clear, specific prompt" requirement on every authenticated page; duplicating that messaging on the save step itself would be redundant, not an improvement.
- **The sealed record reuses `ExamResultsContent`/`EXAM_RESULTS_MIGRATIONS` rather than defining a parallel schema** — the sealed and individually-encrypted copies hold identical content; a future schema change should migrate both the same way, with one registry, not two independently-maintained ones.

## Deviations from the original task description

`docs/TASKS.md`'s M3-016 row describes "encrypt... to the school key." The shipped mechanism does not use the symmetric school key at all — see Flags #1. This is a deviation from the task's literal wording, not from its actual requirement (`FR-SCHOOL-03`/`ADR-0010`'s real intent: admin can read school-wide results, our backend never can, a teacher's individual view is unaffected), which is fully met.

- `apps/api`: `school-members-rls.test.ts`/`school-members-routes.test.ts` updated and re-run against real Postgres (32 tests, all passing) to cover the new column end to end, including a route-level assertion that `GET /schools/my-membership` returns the denormalized `adminX25519PublicKey`.

- `new-exam-client.test.tsx`: two new tests confirming the sync is attempted with the exact saved exam, and that a sync failure never blocks the existing save-and-redirect behavior.
- **End-to-end proof of the task's literal done-when criterion** (`school-result-dual-encryption.e2e.test.ts`): real, unmocked X25519 crypto run through a faithful in-memory Drive fake (parses the actual multipart wire format, tracks real per-folder file state) simulating two genuinely separate sessions — a "teacher session" holding only the admin's public key seals and uploads; a separate "admin session," built from nothing but the admin's full keypair and a fresh download, opens it and gets back the identical content. A wrong-keypair admin cannot open another school's upload. Re-saving the same exam overwrites the school copy in place rather than duplicating it.
- Full `apps/web` and `apps/api` typecheck/lint/test suites run locally (see Current status).
