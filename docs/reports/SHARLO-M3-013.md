# SHARLO-M3-013 — Data versioning/migration framework

**Status: done.** Builds the `schemaVersion` handling `ARCHITECTURE.md` §14 always said every encrypted envelope carries, and fixes a latent design flaw in how that version was actually wired, found while building this.

## Flags

**One real design flaw found and fixed, not escalated — a normal implementation judgment call, not a stop condition.** `M3-006`'s `encryptEnvelope` (`apps/web/lib/storage/envelope-crypto.ts`) had a single internal `CURRENT_SCHEMA_VERSION = 1` constant applied to every envelope regardless of its `type`. That's wrong once two content types need to evolve independently — an exam-results shape change has no reason to force a roster-shape version bump, or vice versa. This had never been exercised (nothing had a second version of anything yet) so it was never caught by a test. Fixed by making `schemaVersion` a required, caller-supplied parameter instead of an internally-guessed constant; each content type's own storage module now owns its own version constant and migrations registry. This is a fix to match `ARCHITECTURE.md` §14's own intent (a per-record version that lets "a future app version detect and migrate older records") more than a scope change, so it's recorded here and in the architecture doc's resolution log rather than treated as a founder-escalation point.

No other flags. The task's own `docs/TASKS.md` done-when criterion ("a v1-shaped fixture record migrates to a deliberately-introduced v2 shape in a test") is met literally, via a dedicated end-to-end test — see below.

## What was built

- **`apps/web/lib/storage/envelope-migration.ts`** — the generic migration-application step. Exports `MigrationFn = (content: unknown) => unknown` and `migrateEnvelopeContent<T>(storedVersion, targetVersion, content, migrations)`, which applies `migrations[storedVersion]`, then `migrations[storedVersion + 1]`, and so on until `targetVersion` is reached. No-op when `storedVersion === targetVersion` (the overwhelmingly common case today). Throws — never silently returns partially-migrated or stale-shaped data — if `storedVersion > targetVersion` (a record written by a newer app version, a real multi-device scenario) or if any hop in the chain has no registered migration function.
- **`apps/web/lib/storage/envelope-migration.test.ts`** — pure-function unit tests in full isolation: no-op at equal versions, a single v1→v2 hop, a multi-hop chain where order matters (confirms migrations apply in sequence, not independently), and both throw paths.
- **`apps/web/lib/storage/envelope-crypto.ts`** — `encryptEnvelope` gained a required 5th parameter, `schemaVersion: number`, written directly into the returned envelope. The internal `CURRENT_SCHEMA_VERSION` constant is removed entirely; this module now stays fully content-agnostic about versioning, matching its existing "knows nothing about any specific type's content shape" design. `decryptEnvelope` is unchanged — it already just returns whatever `ciphertext` decrypts to, with no opinion on shape.
- **`apps/web/lib/exams/exam-results.ts`** — added `CURRENT_EXAM_RESULTS_SCHEMA_VERSION = 1` and an (currently empty) `EXAM_RESULTS_MIGRATIONS` registry. `saveExamResults` passes the version constant into `encryptEnvelope`. A new `decryptAndMigrateExamResults` helper decrypts, then calls `migrateEnvelopeContent` against the stored envelope's own `schemaVersion` before returning typed `ExamResults`; `listExamResults`/`loadExamResults` now go through this helper instead of calling `decryptEnvelope` directly.
- **`apps/web/lib/roster/roster-store.ts`** — the identical pattern: `CURRENT_ROSTER_SCHEMA_VERSION`, `ROSTER_MIGRATIONS`, `saveRoster` passing the version through, and a new `decryptAndMigrateRoster` helper used by `listRosters`/`loadRoster`.
- **`apps/web/lib/storage/envelope-migration.e2e.test.ts`** — a new, dedicated end-to-end test, separate from the pure-function unit tests. Defines a synthetic `migrationFixture` envelope type that exists only in this file (never a real production type), with a `FixtureV1Content` (`{ name }`) and `FixtureV2Content` (`{ name, active }`) shape and one migration between them. Runs a v1-shaped record through the _real_ pipeline — `encryptEnvelope` → an in-memory fake `EnvelopeStore` (same shape used by `exam-results.test.ts`) → `decryptEnvelope` → `migrateEnvelopeContent` — and asserts the migrated result matches the deliberately-introduced v2 shape. A second test confirms a record already written at the target version round-trips with no migration applied, exercising the common-case path through the same real pipeline.
- **`apps/web/lib/storage/envelope-crypto.test.ts`** — updated its 4 existing `encryptEnvelope` calls to pass the new required `schemaVersion` argument.
- **`docs/ARCHITECTURE.md`** — §14's second bullet rewritten to state the per-type model explicitly (it previously read ambiguously, as if one version might apply across every envelope type), describing `migrateEnvelopeContent`'s throw conditions and pointing at this report. New resolution-log item 20 records the fix, and the summary sentence below the log updated from "Items 14–19" to "Items 14–20".
- **`docs/TASKS.md`** — M3-013's row updated to `Status: done` with a summary of what was built and the design-flaw fix.
- **`CLAUDE.md`** — new decisions-log bullet (inserted after the M3-012 bullet) covering the per-type versioning fix, the wiring-now-not-later reasoning, and the exact pattern a future session follows to add a real second version.

## Key decisions

- **Per-type versioning, not one shared version.** `schemaVersion` belongs to a content type's shape, not to the envelope format itself — two types' shapes change on independent schedules, and a shared counter would force an unrelated type to "bump" every time any other type's shape changed, or worse, invite reusing the same number to mean two different things. `envelope-crypto.ts` stays the one place that knows about encryption and nothing about content; each type's own module (`exam-results.ts`, `roster-store.ts`) is the one place that knows its own shape history.
- **Wire the migration-check call into both real call sites now, even though neither type has a real v2 yet.** This was deliberately _not_ treated as speculative scope creep: the alternative — deferring the wiring until a real migration is actually needed — is a TypeScript-silent failure mode. A load function that just decrypts and returns old-shaped content cast to a new type compiles fine either way; nothing short of a runtime shape mismatch would reveal that the wiring was forgotten, and by then the bad assumption may already be baked into UI state. Wiring it now, while the registries are empty no-ops, costs two call sites' worth of boilerplate and closes that gap permanently.
- **Not forcing a real production type to grow an artificial v2 today.** Considered and rejected — inventing a fake shape change on `exam-results` or `roster` just to "prove" the system works would be speculative scope the task doesn't need; a synthetic fixture type in a dedicated end-to-end test proves the same integration (real encrypt→store→decrypt→migrate composition) without polluting a real type's migration history with a throwaway entry.
- **Migrations registries keyed by the _source_ version (`migrations[1]` means "the function that takes a v1 record to v2"), not the target version.** Matches how the unit tests already read (`1: (c) => ...v1 to v2`) and makes the loop in `migrateEnvelopeContent` a direct `for (v = storedVersion; v < targetVersion; v++)` walk with no off-by-one translation needed at the call site.
