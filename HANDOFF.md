## 2. What's fully built and working, in plain language

This section is not a feature checklist — it's what the running system actually does today, so you understand the real product before you touch it.

A teacher signs up either with their Google account (which also grants this app permission to create and read _only the files this app itself creates_ in their Google Drive — never their whole Drive) or, if they'd rather not use Google at all, with just their email address and a one-time code sent to it. Either way, right after signup, the app generates a random encryption key for that teacher and asks them to set a passphrase and save a one-time "Recovery Key" — these are the only two things that can ever unlock their data, and our own servers cannot. If a teacher loses both, their data is permanently gone; the app says this plainly, more than once, and proactively re-reminds them to confirm they've saved the Recovery Key at 7 and 30 days after signup (in-app banner and email) until they actually do.

From there, a teacher creates an exam, picks a bubble-sheet template (one of ours, or a custom one generated from a photo of their own sheet), and scans an answer key by holding it up to their phone or laptop camera — no tap needed, the app detects the sheet, waits for it to be held steady for half a second, and captures automatically (a manual "Take Photo" button is always there too, since auto-capture isn't 100% reliable on every device). Every subsequent student sheet scans against that key instantly. Anything the detection engine isn't confident about — a smudged bubble, two marks on one question, an unreadable roll number — goes into a per-exam "Review Queue" with a cropped image of just that question, for the teacher to resolve by hand; **the system is built to never silently guess an ambiguous mark**, which is the single most important trust property of the whole product. A teacher can also batch-import a folder of scanner-produced images or a PDF instead of scanning live.

Results land in an editable, spreadsheet-like table (name/roll-number/per-question-mark corrections, row add/delete), with a per-question breakdown, class analytics (hardest questions, weakest students, score distribution), and CSV/Excel export — all computed entirely in the browser from the teacher's own decrypted data, never touching our servers in plaintext. A teacher can also upload a CSV class roster once per class and reuse it across every exam for that class, with scanned roll numbers auto-matching to roster names.

For schools: a principal creates a "School" account, which generates a second encryption key scoped to the school and sets up a shared Google Drive location (a real Shared Drive if the school has Google Workspace, a shared folder otherwise — the Shared Drive path gives a real continuity guarantee if a teacher later leaves; the folder path's guarantee is weaker, see §3 below). Adding a teacher to the school shares that Drive location with them and walks them through a one-time Google file-picker step. From then on, every exam that teacher finalizes gets encrypted twice — once to the teacher's own key (their individual view is completely unaffected) and once to the school's key, written into the shared container — so the principal's own dashboard can show school-wide results across every teacher, decrypted entirely in the principal's own browser. Our backend is structurally incapable of ever being part of that decryption — there is no code path anywhere in this codebase, server-side, capable of opening a sealed result; this is enforced by a CI check that fails the build if the backend ever gains a dependency on the one crypto library capable of it, not just a promise.

Removing a teacher from a school revokes their Drive access and (on the weaker, folder-based path only) attempts to transfer ownership of any files they still personally own back to the admin first — see §3 below for the real, flagged doubt about how well that specific mechanism actually works.

None of this — billing, the admin panel, SEO, class/attendance management, exam configuration options (negative marking, multiple sets, grade bands), deeper analytics, manual Excel import, or public result announcements — exists yet. That's M4 through M12, which is what you're building next.

## 3. Known open issues and judgment calls — read every one of these before you touch anything nearby

These are not "nice to know" — several of them are exactly the kind of thing a less experienced developer re-breaks by "fixing" something that isn't actually broken, or builds on top of a gap nobody told them was there. Where one of these says "stop and ask the founder," that means stop and ask the founder — see §5 and `.clinerules`'s stop-and-ask list for exactly what that means in practice.

### 3.1 The two biggest gaps found during this handoff itself (new, not previously documented this clearly)

1. **"Fee Tracker" — one of exactly four pillars the founder has named as locked v1 scope (alongside the core scan/grade loop, Student Progress Tracker, and Attendance) — has _no specification at all_.** No functional requirements, no milestone, no data model, nothing beyond the two-word gloss "teacher tuition tier + principal/school rollup." Confirmed by a full search of the codebase during this handoff: zero `FR-FEE-*` requirement IDs anywhere in `docs/SRS.md`, zero mentions in `docs/ARCHITECTURE.md`'s data model, zero ADR, zero milestone. See `docs/SRS.md` §5.17a for the full account of how this was found and why it can't be guessed at. **Do not build anything for this, do not design a data model for it, do not infer what "rollup" means — this needs an actual requirements conversation with the founder first.** It is not scheduled into any milestone number precisely because there's nothing yet to schedule.
2. **The School-plan "fallback folder path" teacher-removal continuity guarantee may not actually work, and there is no tracked task to resolve this.** When a school doesn't use Google Workspace (so its data lives in a regular shared Drive _folder_ instead of a true Shared Drive), removing a teacher is supposed to transfer ownership of any files they still personally own back to the school admin before revoking their access. Research done while building this (`docs/ADR/0010-school-plan-multi-recipient-encryption.md`'s addendum item 5, `docs/reports/SHARLO-M3-018.md`) found real reason to doubt this works at all without the departing teacher's active cooperation — Google's own ownership-transfer API appears to require the _recipient's_ consent even when the admin is the one initiating it, which would mean this safety mechanism fails silently in exactly the adversarial case (an uncooperative departing teacher) it exists to protect against. **This has never been verified against a real Google Drive account**, and — this is the actual gap — **there is no tracked task anywhere to verify it, fix it, or decide how to handle it before School-plan customers rely on it in production.** This handoff adds that task now: see `docs/TASKS.md` `M7-017` (new, pre-launch-blocking for the School plan specifically, not the individual Teacher plan). Don't let this quietly stay a code comment — it's now a real, tracked, launch-blocking item.

### 3.2 Standing, structural things that look like bugs or oversights but aren't

- **Nothing in this codebase ever "guesses" an ambiguous bubble mark, on purpose, by design.** If you ever find yourself tempted to make the detection engine more "helpful" by resolving an ambiguous case automatically instead of flagging it for the teacher, don't. This is `NFR-ACC-03` in `docs/SRS.md`, and it's treated as the single most important correctness property of the whole product — a regression here is a severe, not a minor, bug.
- **The backend genuinely cannot decrypt student data — this is checked by an automated CI job, not just a design document.** `apps/api/scripts/check-no-decrypt-in-backend.mjs` fails the build if `apps/api` ever gains a dependency on `libsodium-wrappers` or `libsodium-wrappers-sumo` — the only libraries in this codebase capable of opening a sealed cryptographic box. If you ever see this check fail, the right response is almost never "add an exception for my use case" — it means you're about to do something a core product guarantee forbids. Stop and ask (see §5).
- **Google Drive scope is `drive.file` only, enforced by another automated CI job** (`apps/api/scripts/check-oauth-scope.mjs`). If you ever find yourself wanting to request a broader Drive scope to make something easier to build, that's a signal you're solving the problem the wrong way — every prior instance of this exact temptation (creating a Shared Drive, for example) was solved by using Google's file-picker mechanism instead of a broader scope. Don't widen it.
- **The symmetric "school key" column (`schools.school_wrapped_key_by_admin_master_key`) and its helper functions (`generateSchoolKey`/`unwrapSchoolKey`) are dead code, on purpose, left in place rather than deleted.** They turned out to be architecturally unreachable once the actual encryption mechanism was built (see `docs/ADR/0010-school-plan-multi-recipient-encryption.md` addendum item 4) — the real mechanism seals data directly to the admin's personal key instead. Removing a shipped, founder-confirmed column on an engineering guess is a bigger call than any one task's scope — it's flagged for the founder, not deleted. Don't delete it without the founder explicitly saying so, and don't be confused when you see it sitting unused.
- **Every "not verified against a real X" caveat you'll see repeated across `docs/reports/`** (`M1-011`'s real-device validation, `M3-001`'s real iOS Safari, `M3-006`/`M3-014`/`M3-015`/`M3-016`/`M3-017`/`M3-018`'s real Google Drive account) comes from the same root cause: **this project has no real Google OAuth credentials, no real Drive account, and no real phone to test on, configured anywhere — sandbox or CI.** Every test of Drive-touching or detection-engine code mocks the external dependency. This is a known, standing limitation, not a new one each time you see it mentioned — don't re-flag it as if it's a fresh discovery, and don't assume it's been secretly resolved just because a later task doesn't repeat the caveat.
- **`ARCHITECTURE.md` §15's numbered "resolution log" is in chronological order and is additive — never renumber an existing item.** Multiple other documents (`CLAUDE.md`, task reports) cite specific item numbers (e.g., "ADR-0010's addendum item 4"). If you add a new resolution, it gets the next number; if you add a new _addendum item_ to an ADR that already has numbered addendum items, same rule — append, never renumber.

### 3.3 Architectural rules that exist for a specific, non-obvious reason — the reason matters, not just the rule

- **Entitlement checks (which plan an account is on) must be server-sourced, even for a feature that's 100% client-side computation with no server endpoint to call.** This looks contradictory at first — why does a "client-side feature" need a server-sourced anything? Because the alternative is a value the client invents or persists on its own, which a technically sophisticated Free user could simply hardcode to "Pro" and keep forever. The actual design (`ADR-0015`): the client caches a copy of what the server last confirmed, with a bounded freshness window (~24h) and offline tolerance, and re-validates when it reconnects. It is never a live round-trip per check, and it is never a value the client can independently decide for itself. See `docs/SRS.md` `NFR-SEC-12` and `ADR-0015` before building anything that gates a client-only feature by plan.
- **No hand-rolled cryptography, anywhere, ever.** Every cryptographic primitive this codebase uses is either native WebCrypto (AES-256-GCM) or `libsodium-wrappers-sumo` (Argon2id for key derivation, X25519 sealed boxes for the school-key mechanism) — both already integrated, both already the established pattern. If a task seems to need a new cryptographic operation, the answer is "does libsodium already have a primitive for this," never "implement the algorithm yourself," and if libsodium doesn't have it, that's a stop-and-ask, not a build-it-yourself moment.
- **Why Resend instead of self-hosting email, and why never more than one Resend account:** a brand-new server has no sender reputation, and a login/password-reset email landing in spam isn't a degraded experience, it's a user who literally cannot get into their account. Rolling your own mail server, or spinning up a second provider account to dodge a volume cap, both read to mail providers as spam-evasion behavior and can get the _entire sending domain_ blacklisted — a reputation hit that takes months to recover and breaks email for every single user, not just the one who caused it. See `docs/ADR/0011-transactional-email-provider.md`'s addendum for the full reasoning. The correct response to outgrowing Resend's free tier is upgrading to a paid Resend tier. Full stop, no exceptions, no matter how tempting a cost optimization looks.
- **Why integration credentials (Resend, Paddle, Bank Alfalah, any future provider) live in an encrypted database table, never an environment variable:** so the founder can add, rotate, or revoke any of them from the admin panel without you needing to touch a deploy. See `ADR-0017`. If you ever find yourself about to write `process.env.SOME_NEW_API_KEY`, stop — that's very likely a regression against this rule, not a harmless shortcut. The pattern is: add a row to `integration_credentials`, read it through the existing `credential-store.ts` helpers.
- **Why the Free tier's usage cap is never enforced mid-session, even once the server-confirmed count is over the limit:** a teacher mid-way through grading a class of 40 cannot be cut off at student 23. The warning only ever appears at the _next_ app open or on the dashboard. See `docs/SRS.md` `NFR-SEC-07`/`FR-BILLING-06`. This is a product-trust decision, not a technical limitation — don't "fix" it to be stricter because it looks like soft enforcement is a loophole; it's a deliberate, founder-confirmed tradeoff.

## 5. Standing rules, restated in full — not "see CLAUDE.md," the actual rules

Assume you will not reliably re-read or retain `CLAUDE.md`'s full decisions log the way a long-running session would. These are the operational rules you follow on literally every task, restated here in full so there's nothing to infer.

### 5.1 The CI gate rule

**A task is not done until every single check GitHub reports on your pull request's current head commit is green.** Not "the important ones" — all of them, no exceptions. Before you push: run the repo's own `npm run ci` (lint + typecheck + test) locally and confirm it passes. After you push: wait for CI, then check the actual GitHub check-run data (via the GitHub API/CLI tooling available to you) — do not assume a check passed because you didn't see an error, and do not assume a notification means success. If a check fails intermittently, that is **not** a "flake" you're allowed to wave off — find the actual root cause and fix that, the same as any other failure. Re-running the same commit and hoping for a different result is exactly the behavior this rule exists to prevent. You get 3 attempts to fix a CI failure for any one task; if it's still red after 3 real, diagnosed fix attempts, stop, mark the task blocked in its report with the specifics of what failed and what you tried, and move to the next unblocked task — don't loop on it indefinitely.

### 5.2 The push-integrity rule

**Never assume a `git push` succeeded just because the command didn't print an error.** After every push, run `git fetch origin <branch>` and confirm `git rev-parse HEAD` matches `git rev-parse origin/<branch>` before treating the push as done. Every commit must be atomic and complete — never push a commit that's a half-finished change (a migration with no code that uses it yet, for example). If a GitHub Actions run times out, gets cancelled, or ends in any state that isn't a clear pass or fail, treat that exactly like a failing check — investigate why, don't assume "probably fine."

### 5.3 The milestone-gating rule

**Finishing the remaining tasks of an already-authorized milestone is expected and autonomous. Starting a brand-new milestone requires the founder explicitly saying "go" on that specific milestone, every single time — no exceptions, no matter how obviously "next" it looks.** This is not a one-time confirmation that covers everything from here forward. If you finish every M4 task and M5 is next in the list, that is not permission to start M5 — go back to the founder and ask. This exact rule exists because an earlier session on this project once started a new milestone on its own initiative via a misconfigured recurring check-in, and it was treated as a serious process failure when caught, not a minor slip.

### 5.4 The no-hand-rolled-crypto rule

Already covered in §3.3 above — repeating it here because it belongs in this list too. Established libraries only (native WebCrypto, `libsodium-wrappers-sumo`). If a task needs a cryptographic primitive that isn't already in use in this codebase, that's a stop-and-ask, not something to implement yourself even if you're confident you can get it right.

### 5.5 The Free-tier gating rule

Free tier is scanning (camera and batch import) plus basic results (view + CSV/Excel export) — full stop. Every other feature in `docs/SRS.md` is Pro/School, no exceptions, no new "small free allowance" for a new feature unless the founder explicitly says otherwise for that specific feature. See `docs/SRS.md` §5.9a's gating table before building any new feature's plan-gating — it's a literal, specific, feature-by-feature table, not a principle to reapply by your own judgment.

### 5.6 The real-browser verification discipline

**Passing automated tests is not, by itself, sufficient proof that anything touching the detection engine, the crypto, or a binary file format (XLSX, PDF) actually works.** Multiple real bugs in this project's history were invisible to a fully-green test suite and only surfaced when someone actually ran the code in a real browser (a `pdfjs-dist` compatibility bug that broke on real Chromium despite passing every mocked test; an `exceljs` XLSX output that needed checking against a real file's binary signature, not just a mocked write call). For any task that touches scanning/detection, cryptography, or a file format a real external program will open, do not report it done on the strength of a green `npm run ci` run alone — actually exercise it in a real browser or equivalent and say so in the task's report.

### 5.7 The report format

Every completed task gets one file at `docs/reports/<task-id>.md` covering, in this order: (1) Flags first — anything blocked, ambiguous, or deviating from the task's description, and why; say "nothing to flag" explicitly if there's genuinely nothing, don't just omit the section; (2) what was built; (3) key decisions made along the way; (4) deviations from the original task description and why; (5) how it was tested; (6) current status (done / blocked / partial-and-why). This is not a formality — the founder reads these asynchronously to understand what happened without re-deriving it, and whoever picks this project up after you (possibly you in six months, possibly someone else entirely) relies on them the same way you're relying on the ones already here.

### 5.8 Stop conditions — the short version

Stop and flag in the task's report instead of guessing, deciding, or proceeding, when: a task would require touching plaintext student data server-side (the feature needs a different design, not an exception); scope seems ambiguous or contradictory, or like it should move between in- and out-of-scope; a task is blocked on an open architectural decision that hasn't been confirmed; or `docs/TASKS.md` turns out to be missing a real prerequisite. **See `.clinerules`'s stop-and-ask trigger list for the complete, task-specific version of this rule** — it names several additional categories (cryptographic design choices, multi-tenant data isolation, payment/billing logic, scope not covered by the locked four-pillar scope) that are _always_ a stop-and-ask, every time, with no exceptions for "this one seems simple."
